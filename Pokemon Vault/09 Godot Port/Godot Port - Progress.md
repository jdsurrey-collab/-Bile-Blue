### The tileset-alias bug (worth remembering)
The first full export silently dropped **24 maps including Oak's Lab and both Red's House floors** — all with `FileNotFoundError`.

Cause: tileset names are spelled differently in two places, and several are pure **aliases** sharing another tileset's art:

| Map header says | `gfx/tilesets.asm` labels it | Real asset |
|---|---|---|
| `DOJO` | `Dojo_GFX` | `gym` |
| `MART` | `Mart_GFX` | `pokecenter` |
| `MUSEUM`, `FOREST_GATE` | `Museum_GFX`, `ForestGate_GFX` | `gate` |
| `REDS_HOUSE_1/2` | `RedsHouse1_GFX` | `reds_house` |

Deriving the filename from the tileset name *appears* to work because `"OVERWORLD".lower()` happens to be the real file — so Pallet Town passed and hid the problem. Fixed by parsing the stacked labels in `gfx/tilesets.asm` and matching on a normalised key (uppercase, underscores stripped).

**Lesson: a converter that works on the first sample proves nothing.** Run it across the whole corpus early — the failures are where the format's real complexity lives.

### The verification-driver rabbit hole (worth remembering)
Building a synthetic-input test harness surfaced the same "testing each link isn't testing the chain" lesson as the ROM side, in a new shape:

1. **First attempt** toggled press/release on a fixed real-time schedule — raced with scene transitions still inside an unrelated `await` (a fade tween), so a press could fire and release *before* the target scene was even listening.
2. **Second attempt** held the button continuously until an observable check passed — but the game's own scripts correctly use `is_action_just_pressed` (a real button press is a discrete edge, not a held state), which only fires **once**, at the start of a hold. If that single frame doesn't line up with the target's `_process()` (an ordering quirk between an autoload and whatever scene is current), a multi-second continuous hold produces zero further chances.
3. **Fix**: pulse the input in short press/release cycles instead of one continuous hold — each cycle is a fresh edge, giving many independent chances rather than betting everything on one frame.

None of this is a defect in the shipped input code, which is standard, correct practice for real human input. It only matters for *driving* the game programmatically.

## Phase 2 — Seamless overworld & movement 🔄 in progress

User redirect mid-Phase-3: before any more scripted content (cultist dream, etc.), build the **whole connected map** and get **core walk+collision** right everywhere first. Explicit scope from the user: seamless world (walking off an edge continues directly onto the next map, no load screen — GBA-style), and *just* today's plain walk+collision, not ledges/running/bump-animation.

`overworld_map.gd` rewritten from a single-map loader into a multi-map stitched world:

- **`_loaded: Dictionary`** (slug → origin/size/data/texts) replaces one map's worth of state. Tiles, NPCs, warps, signs, and walkability are all now queried in **world-space cells** across every currently-loaded map, not one map's local grid.
- **Two distinct transition types, on purpose:** WARP (door/staircase) is a hard reset — clears everything loaded, places the target at world origin. CONNECTION (walking off an edge) never resets, only **extends** what's loaded, keyed off `on_player_moved()` noticing the player's cell left the focus map's rectangle and entered an already-stitched neighbour.
- **Connection offset math**, decoded from `macros/scripts/maps.asm`'s `connection` macro and confirmed against two real cases: the 4th macro argument is a **block offset** (×2 for cells) of the target's edge relative to the current map's edge — X-offset for north/south, Y-offset for east/west. Verified empirically both ways: Route1↔ViridianCity is a **non-zero** ∓5-block pair (symmetric), Pallet Town↔Route1 is a **zero**-offset pair.
- **`LAST_MAP` sentinel** (a real ROM warp target meaning "wherever the player was standing outdoors before entering this building") resolved via `GameState.last_outdoor_map_slug/cell/facing`, recorded only at the outdoor→indoor transition, never overwritten by indoor→indoor warps.

### Verified by screenshot + coordinates, not just "it compiled"

### Bugs found and fixed while building the driver (all driver-side, not game-side)
- **Walked straight into the player's own front door.** The default spawn sits one tile south of Pallet Town's Red's House warp — the very first "walk up" test correctly triggered a real warp (hard reset), which then freed the player node the driver was still holding a reference to (`previously freed` error). Not a game bug — the warp fired exactly as it should have. Fixed by routing the test path around all 3 known door tiles.
- **`_tap()` press/release pulses were racing the player's own step-tween.** `player.gd` only reads input while idle, and a step's tween runs for a fixed `STEP_TIME`. A pulse shorter than that dropped moves (missed 2 of 5); a pulse longer than that double-stepped (5 taps produced +9 cells). Fixed by replacing fixed-duration pulses with a poll: hold the action down and watch `player.cell` change exactly N times, then release — immune to guessing at timer durations entirely.
- **Eyeballing Route 1's ASCII walkable grid for a "clear column" was wrong** — assumed columns 0-2 were open in every row; actually every row has a wall at x=3, sealing that strip off from the real path. Fixed by BFS-ing the actual `route1.json` walkable array in Python for a real shortest path, rather than reading the grid by eye a second time.

### Automated whole-graph check, not manual per-map walking
Given 221 exported maps, walking each border by hand doesn't scale (matches the port's own "port the engine, don't hand-verify content" rule). Wrote `tools/verify_map_graph.py`: for every connection on every map, checks the target exists, the reverse connection points back with the exact negated offset, and — placing both maps at their computed origins — the shared border actually has overlapping walkable cells (a numerically-valid offset with zero real walkable overlap would still "connect" but be unusable).

Result: 8 flagged borders, all explained, none are port bugs:
- `pallet_town↔route21`, `cinnabar_island↔route20`, `route19↔route20` — sea routes, all-water on the border. Real Gen 1 geometry; unwalkable until Surf is implemented (not yet built).
- `route22↔route23` — Route 22's north edge is a **solid tree border** in the real `.blk`/blockset/collision data (checked block IDs `0x0d`/`0x13`/`0x20`/`0x21`/`0x28`/`0x2c`/`0x2b` against `Overworld_Coll`'s walkable-tile-ID list by hand — every tile in every one of those blocks is non-walkable). Matches pret's own `; unnecessary` comment on that connection in `data/maps/headers/Route22.asm`. A faithfully-reproduced vanilla quirk, not an export defect.

### Warps verified end-to-end too (door in, stairs up/down, LAST_MAP back out)
`verify_world.gd` only proved CONNECTIONS (walking off an edge). Warps are the other half of "core walk+collision" and needed their own driver (`scripts/dev/verify_warps.gd`, same reverted-after-use treatment): Pallet Town's front door → Red's House 1F → stairs → 2F → stairs back down → back to the exact door → `LAST_MAP` restoring the precise outdoor cell. All 8 assertions passed (exact cell match at every hop, not just "a warp happened").

Two more real, driver-independent findings surfaced along the way:
- **Red's House 1F has two adjacent door tiles**, (2,7) and (3,7), both → `LAST_MAP`. A path that swept along row 7 stepped onto the second one mid-walk and correctly warped back outside before the test meant to trigger it — real game behaviour, not a bug; the fix was routing the test through row 6 (no warp tiles) and only touching a door tile on the deliberate final step.
- **The stairs tile is a warp too, and arriving there by *walking* triggers it immediately** (unlike arriving by *spawn placement*, which doesn't run `_check_warp()` at all) — so ascending needed no special dance, but descending (arrived at 2F via spawn) needed a deliberate step-off-then-back-on to fire.

### Real bug found and fixed: small indoor rooms showed as half-blank gray
Every screenshot inside Red's House showed roughly half the frame as flat gray. Root cause: `Camera2D.limit_*` in Godot clamps the *viewport's edges* to stay inside the limit rect, not the center point — for a room smaller than the 160×144 viewport (Red's House is 128×128), a limit span narrower than the viewport is a degenerate/inverted case. Confirmed empirically (not just by inspection) by printing `cam.get_screen_center_position()`: a first fix attempt that collapsed `limit_left == limit_right` to the room's center produced `screen_center=(-16, 136)` instead of the intended `(64, 64)` — Godot's real per-axis clamp order resolves the inverted range asymmetrically, not to the midpoint. Fixed in `overworld_map.gd`'s `_update_camera_limits()` by sizing the limit span to *exactly* the viewport dimensions (centered on the room) instead of collapsing it to zero width — mathematically the same "locked to center" result, but it no longer trips the degenerate case. Confirmed fixed the same way: `screen_center` now reads exactly `(64, 64)` on every indoor shot, and the room renders centered with only the real Game-Boy-accurate thin margins (most Gen 1 interiors are smaller than a full screen).

## Pokémon data moved to real Godot Resources

Per explicit user direction: species/moves stop being raw JSON dictionaries at runtime and become proper Godot `Resource` classes — Inspector-editable, type-checked, and scalable to "many many more" species without touching a registry.

**New classes** (`scripts/resources/`): `PokemonSpecies` (identity/physical/base-stats/typing/moves/evolution/presentation, grouped with `@export_group`), `MoveData`, plus two small link resources — `LearnsetEntry` (level + move) and `EvolutionEntry` (method/target/level/item). `EvolutionEntry.target` stays a plain species-name String rather than a direct resource reference, so evolution data doesn't force eager-loading every species a given one can evolve into.

**Generated, not hand-authored**: `tools/generate_pokemon_resources.gd` (run via `godot --headless --script res://tools/generate_pokemon_resources.gd`) converts `data/species.json`/`data/moves.json` (already-exported ROM data) into one `.tres` per move (170, `resources/moves/`) and one per species (240, `resources/species/`). Matches the port's standing rule: convert the data, don't hand-build content.

**Real bug caught before it shipped: moves were embedded as private per-species copies, not shared.** The first generation pass produced correct-looking output, but every species' `.tres` inlined its own full private `[sub_resource]` copy of each move it knows — editing `resources/moves/tackle.tres`'s power in the Inspector would have changed *nothing* for any species, since none of them actually pointed at that file. Cause: `ResourceSaver.save(res, path)` does not retroactively make the in-memory `res` behave as an external reference just because it was written to disk once — only a `load()`ed instance reliably carries `resource_path` in a way the saver recognizes as "link to this file" rather than "embed a copy." Fixed by re-`load()`ing each move immediately after saving it, and using *that* instance (not the original just-created object) when wiring up species' `level1_moves`/`tmhm`/`learnset`. Confirmed fixed by reading the regenerated `.tres` text directly: species files now contain `[ext_resource type="Resource" path="res://resources/moves/tackle.tres"]` and reference it, instead of a duplicated `[sub_resource]` block — one shared move definition, referenced everywhere, which is the entire point.

**`GameData` autoload now loads by directory scan, not a hardcoded list** — `_scan_resources()` walks `resources/species/` and `resources/moves/`, keying each by the resource's own `species_name`/`move_name` field. Adding species #241 means adding one `.tres` file (generated or hand-authored directly in the Inspector via New Resource → PokemonSpecies) — no code change. `get_species()`/`get_move()`/`species_by_dex()`/`species_by_index()` now return typed `PokemonSpecies`/`MoveData` instead of `Dictionary`; the one existing consumer (`title_screen.gd`'s mon-cycling display) was updated from a `sp.get("front_sprite")` path-string lookup to a direct `sp.front_sprite` Texture2D reference.

One known data quirk carried over from the ROM, not a bug in the new pipeline: Mew's TM/HM compatibility list includes a genuine vanilla placeholder move named `UNUSED` with no real move behind it — the generator warns and skips it rather than crashing.

**Two workflows now coexist for editing a species/move, and they don't automatically merge**: regenerate from `data/species.json`/`data/moves.json` (bulk resync after a ROM-side change) overwrites the `.tres` wholesale, OR hand-tune fields directly in a `.tres`'s Inspector for balance work (quick, but a later regen stomps it — reapply by hand, or make the tweak in the JSON instead so it survives regeneration).

**Update**: front/back sprite export is now done too (see Phase 1 above) — every species' `front_sprite`/`back_sprite` is populated, confirmed live via the title screen's cycling mon actually rendering a sprite for the first time instead of nothing.

## Crisp HD text/UI, pixel-art world unchanged

User-flagged: dialogue/menu text looked blurry. Root cause: `project.godot`'s `window/stretch/mode` was `"viewport"` — that mode renders the *entire* game (world **and** UI) into one small 160×144 buffer and blits the whole thing upscaled as a single image, so text glyphs get rasterized at their tiny native size and then blurred/blocked by the upscale, with no way to fix it per-scene.

Fixed with a single project setting, no scene changes needed: switched to `window/stretch/mode = "canvas_items"` (+ `aspect = "keep"`). In this mode Godot scales the *canvas transform* instead of pre-rendering to a small buffer, so each CanvasItem draws at the real output resolution — dynamic font rasterization is transform-aware and comes out genuinely crisp/anti-aliased, while sprites/tiles keep rendering pixel-perfect through the project's existing nearest-neighbor `default_texture_filter`. Confirmed by screenshot, not assumed: the status screen's text went from visibly blocky to properly smooth, and the same screenshot shows the overworld's houses/trees/player sprite still perfectly crisp pixel art right behind the panel — exactly world-stays-retro, UI-goes-HD, with zero per-scene rework.

Regression-checked against every existing verified flow (intro → title → menu → Oak → naming → overworld, plus the full party/save/menu chain) — all pass identically to before. The pre-existing `verify_intro.gd` flakiness (see above) showed up at a similar rate as before this change (~3/5), not meaningfully worse — not something this change introduced.

**Standing principle going forward**: build all new UI (battle scene included) as ordinary Control/Label nodes the same way as the existing menus — this stretch mode makes that automatically crisp, no special-casing needed per screen.

## Phase 4 — Battle engine ✅ core done and verified (content-breadth deferred, see below)

The largest remaining phase, broken into sub-passes rather than one push. First sub-pass: `BattleMath` (`scripts/battle/battle_math.gd`), the pure Gen 1 formula layer everything else builds on.

**Read directly from `engine/battle/core.asm`, not recalled from memory** — Gen 1's real formulas have several load-bearing quirks a generic "Pokemon damage formula" reference gets wrong, so every piece was traced to its actual routine before being ported:
- **A critical hit is not "double the final damage."** It's two separate things, both real, both required: (a) the attacker's attack stat and the defender's defense/special use their **unmodified base value**, ignoring stat-stage boosts/drops entirely on both sides, and (b) the attacker's **level is doubled** in the base formula. Confirmed from `GetDamageVarsForPlayerAttack`'s actual instruction sequence (`sla e` doubles level; the crit branch re-reads the stat straight from the party struct instead of the stage-modified in-battle copy).
- **Focus Energy has a real, famous bug**, preserved deliberately: it shifts the crit-chance calculation the wrong direction in `CriticalHitTest`, making crits **less** likely (1/4 of normal) instead of more.
- **High-crit-ratio moves (Karate Chop, Razor Leaf, Crabhammer, Slash) are 8x, not a flat "high" chance** — traced from the actual shared instruction path: both the normal and high-crit branches share one doubling step, then diverge (normal path halves once more, high-crit path doubles twice more instead), netting exactly 8x.
- **Dual-type effectiveness is two SEPARATELY floored integer steps** (`damage = floor(damage * mult/10)`, once per matching defending type), not one combined float multiply — this reproduces a real quirk where a 2-3 damage hit at 0.25x total effectiveness can floor to 0 across the two steps and the game calls that a miss, not "0 damage dealt."
- **Even "100% accuracy" is 255/256, not 100%** — `percent` in `data/moves/moves.asm` compiles to `* 255 / 100`, so 100% becomes byte 255, and the hit check is `random(0-255) < accuracy`, never `<=`.

**Verified against 30 hand-computed assertions** (`scripts/dev/test_battle_math.gd`, wired as a temporary autoload — same pattern as every other dev driver), not just "code that reads correctly": exact base-damage arithmetic worked by hand, STAB rounding, the 0.25x-floors-to-0 quirk using a real double-resist in this roster (Omastar/Omanyte, Rock/Water, each resisting Fire at 0.5x), crit chance for normal vs. high-crit-ratio moves vs. the Focus Energy bug, the accuracy-byte ceiling, and stat-stage ratios at the extremes. All 30 passed.

**A real, non-obvious tooling limitation hit and worked around**: the first test-driver attempt used the `--headless --script` entry point (`extends SceneTree`), the same pattern `tools/generate_pokemon_resources.gd` uses successfully — but that script never actually referenced an autoload by name. ## Real bug, user-reported: indoor rooms sometimes render as a flat gray blob, no stairs visible

User report: the starting room (Red's House 2F, with the cultist) showed as solid gray with no furniture, no visible stairs, and no way to tell where the door/stairs were. This was NOT the earlier small-room camera bug (already fixed, see above) — that one left the room too small on screen with correct content; this one made the content itself invisible.

**Root cause, found by direct comparison of requested vs. round-tripped values, not by guessing**: `_source_id_for()` (`overworld_map.gd`) computed each tileset's Godot `TileSet` atlas source id as `abs(tileset.hash()) % 100000` — fine for the `TileSet` itself (`add_source()`/`has_source()` both confirmed the full-range id, e.g. 91030, was accepted and stored correctly), but a **cell's own reference to that source**, set via `TileMapLayer.set_cell()`, silently wraps through an internal 16-bit field. `91030 - 65536 = 25494` — exactly the value `get_cell_source_id()` read back immediately after `set_cell(coords, 91030, ...)`, on the very same call. Every painted cell pointed at a source id that didn't exist, and Godot's fallback rendering for that is a flat gray tile — not an error, not a crash, just silently wrong. This isn't documented Godot behavior; it was found by printing the requested id next to the round-tripped one and noticing the difference was exactly 2^16.

**Critical detail: this bug is non-deterministic across separate game launches.** Godot's `String.hash()` is not guaranteed stable from one process run to the next, so whether `"reds_house".hash() % 100000` landed above or below the 65536 wraparound point was pure chance *per launch* — explaining why earlier testing sessions this same pass (`verify_warps.gd`, screenshotted and passing) showed correctly-rendered interiors while the user's own play session hit solid gray. Same code, different luck of the draw. Fixed by capping the modulo at 30000 (`% 100000` → `% 30000`) — safely under both the 16-bit wraparound point and the signed-16-bit boundary, so no possible hash value can trigger this again, by construction rather than by chance.

Also fixed in the same investigation, a real second bug: `Overworld._ready()` always loads its `@export` design-time default (`"pallet_town"`) the instant the scene is instantiated, and only *then* does `SceneFlow`'s own `load_map(START_MAP)` call fire on top of it for a fresh New Game. `load_map()`'s hard reset cleared the tracking dictionary (`_loaded`) but never actually erased the TileMapLayer's previously-painted cells — so Pallet Town's much larger tile footprint stayed visually painted underneath/around whatever loaded next, bleeding through as checkerboard grass/tree tiles at the edges of any indoor room smaller than the viewport. Fixed with one line, `_tiles.clear()`, added to `load_map()`'s reset sequence before the new map stitches in.

Verified by screenshot after each fix, and re-verified together: Red's House 2F (the cultist's room) and Red's House 1F both now show full detail — bed, TV, computer, bookshelves, table, plant, and the staircase clearly visible — across multiple repeated fresh-launch runs, plus a full re-run of the existing warp-flow assertions (all still passing) to confirm neither fix broke the warp mechanics themselves.

### Two real bugs found and fixed while verifying, not while writing

**1. `ChoiceMenu` could resolve to its default option before ever becoming visible.** `ChoiceMenu` and `Dialogue` are both autoloads, processed once per frame in `project.godot`'s registration order — `ChoiceMenu` comes *after* `Dialogue`. A script's normal pattern (`await _say(...)` immediately followed by `await ChoiceMenu.ask(...)`) means: the tap that closes a dialogue's last page fires `Dialogue.advance()` → `close()` → `finished` signal, which resumes the awaiting script *synchronously*, which calls `ChoiceMenu.ask()` and sets `is_active = true` — all still inside `Dialogue._process()`'s call frame. Later that *same* frame, `ChoiceMenu._process()` runs (autoload order) and reads `Input.is_action_just_pressed("interact")`, which is still `true` for that whole frame — instantly confirming the freshly-opened menu's default selection (0) before it was ever drawn. Not a test artifact: a real player pressing A to dismiss the last line of dialogue right as a menu appears would get exactly this, a choice they never got to see or make. Caught by a headless dev-verify driver whose check-before-tap loop never once observed `is_active == true`, yet the choice had already resolved. Fixed with a one-line `await get_tree().process_frame` at the top of `ChoiceMenu.ask()`, deferring activation past the stale input frame (`scripts/autoloads/choice_menu.gd`).
- **Lesson for any future autoload-to-autoload handoff in this project**: a signal callback that opens a second input-driven autoload mid-frame inherits whatever input state was already true that frame, regardless of registration order — the receiving system needs to explicitly wait a frame before trusting `is_action_just_pressed`, it can't assume "just became active" means "just received fresh input."

**2. Fresh saves could never leave the house — a real, pre-existing softlock, not something this session's new code introduced.** `GameState.last_outdoor_map_slug` defaults to `""`. The front door (`scripts/RedsHouse1F.asm`'s `warp_event 2, 7, LAST_MAP, 1`) is a genuine `LAST_MAP` warp in the ROM data — real Gen 1 relies on `wLastMap` defaulting to `$00` (`PALLET_TOWN`'s own map constant) on freshly zero-initialized WRAM, a coincidence a Godot `String` has no equivalent of. `warp_to()`'s existing `LAST_MAP` handling already does the right thing (`push_warning` and no-op) when nothing has been recorded yet — which is exactly the problem: on a true fresh save, *nothing has been recorded yet*, so the front door does nothing at all. Never caught before because every earlier dev-verify driver stopped at "entered the overworld" or "cultist dream done" — none of them tried to walk out the front door. Fixed by explicitly seeding `last_outdoor_map_slug`/`cell`/`facing` to Pallet Town, just outside Red's House's own door, in `GameState.reset_for_new_game()` — making the port's default explicit instead of relying on an accidental zero-value coincidence that doesn't carry over from Z80 to GDScript.
- **Lesson**: a verification driver that starts from "already past the tricky part" (Battle scene already loaded, already in the overworld) is real coverage for what it tests, but it's not evidence the *approach* to that state actually works — this bug lived entirely in the one connective step no test had ever walked through end to end.

## Cookie-cutter NPC system: every NPC gets Dialog/Battle/Movement/Reward data

User-directed architecture: rather than hand-writing bespoke behavior per NPC as content work reaches each one, every NPC in the game now gets the exact same four data slots, left blank by default and overridden per-NPC in one place. This is the base every future NPC (trainer, quest-giver, patrol guard, ambient talker) builds on.

**The four resource types** (`scripts/resources/npc_dialog_data.gd`, `npc_battle_data.gd`, `npc_movement_data.gd`, `npc_reward_data.gd`, all plain `Resource` subclasses):
- `NPCDialogData` — `lines`, `one_time` (tracked via a GameState flag), `repeat_lines` (shown after the one-time line or after a battle is won).
- `NPCBattleData` — `party` (species/level/tier; only `party[0]` is used so far since `Battle` only supports one active mon per side, but a real multi-mon party can already be authored here and will be picked up automatically once `Battle` grows that support), `challenge_lines`, `defeat_lines`.

- `NPCRewardData` — `money`, `items`, `flag_on_complete`. `GameState.money`/`GameState.items` are new (save/load-wired) — no bag/shop UI reads them yet, this is the data layer built ahead of it.

Deliberately empty right now — every NPC in the game gets blank defaults until a specific `npc_id` gets an entry. Adding one NPC's battle/dialogue/patrol/reward later is data in this one file, not new code.

**`npc.gd`** now resolves all four resources in `setup()` and exposes a single `interact()` entry point that decides dialogue vs. battle itself — `player.gd`'s `_try_interact()` no longer knows anything about what a specific NPC does, it just calls `npc.interact()` (cookie cutter: every NPC is called the same way). Left blank, dialogue falls back to the NPC's real exported ROM `text_id` lookup exactly as it worked before this system existed, so every ambient NPC in the game keeps talking exactly as before with zero overrides needed.

**`BattleLauncher`** (autoload, `scripts/autoloads/battle_launcher.gd`): the "every NPC can trigger the one main battle scene" piece, extracted from what was originally a private helper inside `oakslab.gd` for the rival fight. `oakslab.gd` now calls the same shared `fight()` function instead of duplicating the scene-swap dance a second time.

**A real bug found and fixed, the same underlying class as several earlier this session (register-clobbering `farcall`s, use-after-free coroutines)**: the first version ran the whole "challenge line → fight → reward → defeat line" sequence as a method on the `Npc` node itself (`_start_battle()`), awaited from `interact()`. This silently broke every single thing after the `await BattleLauncher.fight(...)` call — no flag set, no reward applied, no defeat line, `script_active` never cleared — with no error. Root cause: `fight()`'s scene swap tears down and rebuilds the whole Overworld scene, which frees the Npc node along with it, since it's a child of that scene. A coroutine suspended mid-`await` on a since-freed Node's own method does not reliably resume, even for code that no longer touches the freed instance's fields — the resumption mechanism itself is tied to the (now invalid) script instance. Fixed by moving the entire continuation into `BattleLauncher.run_npc_battle()` — an autoload, immune to the scene swap it itself performs — with `npc.gd` reduced to just kicking it off, unawaited, exactly like `MapScripts.run_on_enter()`'s existing fire-and-forget pattern. **Lesson for this exact codebase**: any coroutine that needs to keep running past a `change_scene_to_file` must be rooted in something that survives the swap (an autoload, or a `RefCounted`-based static class like the existing `OaksLabScript`/`PalletTownScript`) — never a plain scene-tree Node method, even carefully avoiding `self` references in the code that runs after the freed point isn't enough on its own.

Verified with `scripts/dev/verify_npc_system.gd` (temporary autoload): a real override on Pallet Town's fisher (a battle, a money+item reward, a 2-step patrol) — interacting triggers a genuine battle, winning sets the defeated flag and applies the reward exactly (money and item quantity both exact matches), re-interacting afterward does not re-trigger the battle, and the patrol data visibly moves the NPC. ## Real bug, user-reported: NPC dialogue looped instead of closing and waiting for another interact

Same underlying class of bug as choice_menu.gd's ask() fix, mirrored. `Dialogue` is an autoload and processes before scene-tree nodes each frame. On the exact press that closes a dialogue's final page: `Dialogue._process()` runs first, sees `is_active` still true, advances past the last page, and `close()` flips `is_active` to false — all before `player.gd._process()` runs later that SAME frame. player.gd's own gate (`if Dialogue.is_active or ...: return`) now reads `is_active == false` and falls through, and `Input.is_action_just_pressed("interact")` is still true for that whole frame (same press, not consumed by Dialogue's own check) — so `_try_interact()` fires again, finds the same NPC still standing there, and reopens the exact same dialogue with no real second press from the player.

Fixed with the mirror of the ChoiceMenu fix: that one deferred an OPEN by a frame (`await get_tree().process_frame` before `ChoiceMenu.ask()` sets `is_active`), this one defers a CLOSE's effect on other listeners by a frame instead. `Dialogue.close()` now stamps `_closed_at_frame = Engine.get_process_frames()`, and a new `Dialogue.closed_this_frame()` check was added alongside `Dialogue.is_active` in player.gd's movement/interact gate — so the frame a dialogue closes still reads as "blocked" to player.gd, and only the NEXT frame's genuinely-fresh input can re-trigger an interact.

Verified with `scripts/dev/verify_dialogue_no_loop.gd` (temporary autoload): talked to Pallet Town's unmodified girl NPC, clicked all the way through to close, then waited 10 frames with zero further input and confirmed dialogue stayed closed (the reported loop is gone) and movement works immediately afterward. Incidentally also resolved the one uncertain failure from the cookie-cutter NPC system's own verification pass (the girl's ROM-fallback dialogue opening at all) — confirming that earlier failure really was simulated-input flakiness, not a real bug, since this driver's very first assertion (opening her dialogue) now passes cleanly.

**Lesson, worth restating since it's now been hit twice in one session in mirror-image form**: any two systems in this project that (a) are both autoloads processed once per frame, (b) poll `Input.is_action_just_pressed` directly rather than consuming events, and (c) have one system's state change able to unblock or trigger the other within the same frame -- are at risk of this same-frame cascade, in whichever direction the state changes. Opening a gated system needs a deferred-activation guard (ChoiceMenu); closing one that other systems gate on needs a deferred-effect guard (Dialogue). Check both directions before adding the next gated popup/menu system.

## Cookie-cutter wild encounter system: EncounterZoneData + EncounterRegistry

User-directed, explicitly requested as a foundational system before continuing story content: grass/water/cave zones that roll a per-step chance to trigger a wild battle, with the species/level pulled from a weighted 10-slot table matching the ROM's real structure exactly.

**`EncounterZoneData`** (`scripts/resources/encounter_zone_data.gd`, a `Resource`): `encounter_rate` (per-step trigger chance out of 255, matching `def_grass_wildmons`'s rate byte directly) and `slots` (up to 10 entries, `{"species": ..., "level": ...}` or a `level_min`/`level_max` range, ordered commonest-first). `SLOT_CHANCES` is the exact `[51, 51, 39, 25, 25, 25, 13, 13, 11, 3]` from `data/wild/probabilities.asm`'s `WildMonEncounterSlotChances` — shared and fixed, never per-zone, since the ROM itself never varies it either. `roll_wild_tier()` mirrors `data/pokemon/tier_chances.asm`'s real weighting (`[90, 51, 36, 26, 18, 13, 9, 6, 4, 3]` for tiers 1–10) for CLAUDE.md item 5's hidden-tier system, applied to every wild-caught mon.

**Real data, not a placeholder**: Route 1 is seeded with its actual raw 10-slot table, transcribed from `data/wild/maps/Route1.asm` (cross-checked against `Pokemon Vault/07 Kanto Reborn/Encounter Map - Locations & Rates.md`, now a standing CLAUDE.md reference for this exact purpose) — not the vault table's human-merged view, which collapses Pidgey (slots 0 and 4) and Rattata (slots 1 and 3) into one combined-percentage row each; the raw per-slot data is what `SLOT_CHANCES` actually indexes against, so using the merged view would have silently mispositioned two species.

**A real Godot-CLI gotcha hit while verifying**: a fresh `class_name`-declared script (`EncounterZoneData`) failed to resolve anywhere it was referenced (`Identifier "EncounterZoneData" not declared in the current scope"`), cascading into autoload load failures, on a plain `godot --headless --quit-after N` run — even on a second run. Global script classes are indexed by the editor's own filesystem scan, which a pure game-mode headless launch never performs. Fixed with one throwaway run of `godot --headless --editor --quit-after 10 --path .` first (visibly logs `update_scripts_classes: ... EncounterZoneData`), which writes the project's global class cache to disk; every following headless run picked it up normally. Worth remembering for any future new `class_name` file in this project — it's a one-time cache-warm, not a real bug, but the error output alone doesn't say so.

Verified with one passthrough (`scripts/dev/verify_wild_encounters.gd`, temporary autoload): spawned with a living party on Route 1's real open grass, walked in place until an encounter triggered (31 steps, reasonable for a ~9.8%/step rate), and got a real wild Pidgey Lv3 — an exact match for slot 0 of the real table. ## Real bug, user-reported: wild encounters didn't return the player to the same spot, and the HP bar snapped instantly

Two unrelated fixes, both in `scripts/autoloads/battle_launcher.gd`/`scripts/battle/`.

### Return position: two compounding bugs, both root-caused before either fix landed

**Bug 1 — `map_slug` went stale across a stitched seam.** `overworld_map.gd`'s `on_player_moved()` shifts focus between already-loaded maps by updating its own private `_focus_slug`, but never touched the exported `map_slug` field — which `SaveSystem` and `BattleLauncher` both read expecting it to mean "the map the player is standing on right now." `load_map()` itself (any warp) already keeps `map_slug` correct, so this only broke the *seamless walk-across-a-border* case — walking from Pallet Town straight into Route 1's grass with no warp involved, the single most common way any wild encounter actually happens. A battle triggered there would capture the stale slug (still `"pallet_town"`) as where to return to. Fixed by setting `map_slug = slug` alongside `_focus_slug = slug` in `on_player_moved()`.

**Bug 2 — the player's cell is world-space, but a non-focus map's stitched origin usually isn't zero.** `BattleLauncher.fight()` captured `player_node.cell` directly as the return position, on the same (now-corrected) reasoning `oakslab.gd` already used for indoor maps ("always loads at origin zero"). True for an indoor map or a map just warped into — false for any outdoor route reached by walking in from a neighbour, which keeps whatever origin `_extend_neighbours` computed when it was stitched, almost never zero. `warp_to()`'s own `LAST_MAP` bookkeeping already solves this exact problem (`player.cell - cur.origin`); `overworld_map.gd` now exposes that conversion as a reusable `local_cell(slug, world_cell)`, and `fight()` uses it.

**Why no earlier encounter test caught either bug**: every wild-encounter dev-verify driver so far (Route 1, Viridian Forest, the bulk-population spot check) called `map.load_map(route_slug)` directly to spawn the player, which makes that route the fresh origin-zero focus map immediately — world and local cells coincide trivially in that setup. The bug only exists on the path a real player actually takes: walk there from a neighbouring map. This session's fix driver (`scripts/dev/verify_fixes.gd`) deliberately walks from Pallet Town across the real seam instead.

**A third bug, found only once the first two were already fixed and the position was STILL wrong**: `Overworld._ready()` unconditionally auto-loads its design-time default map (`"pallet_town"`, the `@export var map_slug` literal) the instant the scene is instantiated — the same hazard `load_map()`'s own "stale tile bleed-through" fix (Phase 5 notes, above) was written to guard against, but that fix only cleared stale tiles, it didn't address this. That auto-load's own `_spawn_player()` call reads-and-resets `GameState.pending_spawn` as a side effect, regardless of what it was set to beforehand — so `fight()` setting `pending_spawn` to the correctly-computed local cell *before* the scene swap meant the real value got silently eaten by this unrelated, incidental auto-load before `fight()`'s own explicit `load_map()` call ever ran; the player then fell back to the map's default/center spawn point. Fixed by moving the `pending_spawn`/`pending_facing` assignment to *after* the scene swap and its settling frames, immediately before the real `load_map()` call — so the incidental auto-load's consumption lands on harmless leftover state instead.
- **Fixed in a later pass** (see "Fixed: `SceneFlow.continue_game()`'s `pending_spawn`-ordering bug" further down) — `SceneFlow.continue_game()` had this exact same buggy ordering, flagged here and left for a follow-up at the time.

Verified with `scripts/dev/verify_fixes.gd` (temporary autoload): walked the player from Pallet Town across the real stitched seam into Route 1 (not a direct `load_map()`), confirmed `map_slug` updates correctly on the crossing, triggered a real wild encounter, forced a win, and confirmed the player returns to the exact same map *and* the exact same local cell — converting the pre-battle world cell to local coordinates for the comparison, since Route 1's own stitched origin differs before and after the battle (a live illustration of exactly the bug being fixed).

### HP bar: animated drain, double speed on a critical or super-effective hit

`BattleMath.apply_type_effectiveness()` gained a new `"multiplier"` field (the raw combined effectiveness, e.g. `4.0` for Water vs. Rock/Ground) alongside its existing `"damage"`/`"immune"` — non-breaking, existing callers only read the fields they already used. `Battle.mon_changed`'s signal signature grew a `fast: bool` parameter, set true only for the specific damage instance that was a critical hit or `>=2x` effective (every other HP change — drain-heal, recoil, residual poison/burn, `HEAL_EFFECT` — passes `false` explicitly, since none of those are a "hit landing" in the sense asked for). GDScript signal declarations can't carry a default value (a real parse error hit and fixed along the way — `Signal parameters cannot have a default value`), so every `emit()` site in `battle.gd` passes both arguments explicitly; the *receiving* `_on_mon_changed(side, fast = false)` in `battle_scene.gd` is where a default actually lives, for backward compatibility.

`battle_scene.gd`'s HP bars now tween toward the real HP fraction instead of snapping (`_animate_hp_bar`), with duration derived from *how far* the bar has to travel at a fixed fraction-of-bar-per-second rate (`HP_DRAIN_RATE = 0.6`, `HP_DRAIN_RATE_FAST = 1.2`) — not a fixed duration, so a big hit visibly takes longer to drain than a small one, matching a real Pokémon game's feel rather than a uniform-speed slide. A tween already in flight is killed and replaced if a new hit lands mid-drain, so back-to-back hits redirect smoothly instead of queuing up. The initial battle-start refresh (`setup()`) still snaps instantly (`_refresh_all()`/`_set_hp_bar_instant`) — a bar animating up from empty at battle start would look wrong.

Verified in the same pass: `BattleMath.apply_type_effectiveness("WATER", "ROCK", "GROUND")` confirmed as an unambiguous, RNG-independent 4.0x case (so `fast_hit` would correctly trigger) against a neutral 1.0x control (would correctly not); `HP_DRAIN_RATE_FAST` confirmed exactly double `HP_DRAIN_RATE` by reading the constants directly off the live script rather than hardcoding the expected numbers into the test; a live battle hit sampled shortly after landing showed the bar partway between its old and new width (not yet snapped), then confirmed to reach the exact correct final width once given time to finish.

## Architecture pivot: encounter zones rebuilt as real Godot scenes, superseding `EncounterRegistry` above

**The governing reason, from the user directly**: *"I want the philosophy behind this godot project as almost a Pokemon Game editor — I want to be able to simply edit and change systems in godot. Ideally, what I envision, is a scene per encounter zone using a rectangle collision (or something similar) where I can go into godot, use its gui to add or change values within that specific zone. The zones will ALWAYS be rectangle straight lines and I would like to adjust them myself and not always need you to help."* This directly reverses the "per-cell data, not Area2D physics" decision recorded above — that decision optimized for headless-driver testability; this one optimizes for the user's own hands-on editing, which is the higher-priority goal going forward. The trigger was a real reported bug: encounters firing outside the intended area, traced to `EncounterRegistry`'s `cells: null` meaning "every walkable cell on the whole map," which is too broad the moment a map isn't almost-entirely grass.

**`EncounterRegistry` (autoload, dictionary-based) is retired** — deleted along with its bulk-verify test. Replaced by three pieces:

- **`EncounterSlotData`** (`scripts/resources/encounter_slot_data.gd`, `class_name`, extends `Resource`) — one wild-encounter slot as real typed Inspector fields (`species: String`, `level_min: int`, `level_max: int`), replacing a raw `Dictionary` entry so the Inspector renders proper fields instead of a generic dictionary editor.
- **`EncounterZoneData`** (`scripts/resources/encounter_zone_data.gd`, reworked in place) — now holds `slots: Array[EncounterSlotData]` instead of `Array[Dictionary]`; `SLOT_CHANCES`/`TIER_CHANCES`/`should_trigger()`/`roll_encounter()`/`roll_wild_tier()` all unchanged.
- **`EncounterZone`** (`scripts/world/encounter_zone.gd`, `class_name`, extends `Area2D`) — a real `Area2D` with a `CollisionShape2D`/`RectangleShape2D` child, which gives Godot's built-in editor drag-handles for free (no custom `@tool`/gizmo code needed). `@export var data: EncounterZoneData`. `get_cell_rect()` converts the shape's `global_position`/`size` from pixels to cell coordinates (`CELL_PX = 16`); `contains_cell(world_cell)` is a plain `Rect2i.has_point()` check. Using `global_position` means zone math needs no manual per-map origin subtraction — a zone's container sits at that map's real stitched-world pixel origin, so Godot's own transform hierarchy resolves world position automatically, both in-editor (container at origin, so global == local) and at runtime (container offset into the stitched world).
- **`EncounterZoneContainer`** (`scripts/world/encounter_zone_container.gd`) — root script for every per-map placement scene. `zones()` walks its children for `EncounterZone` instances. `_ready()` hides a `Backdrop` child if present — a plain, non-`@tool` script, so this only ever runs at real gameplay time, never while the scene is open for editing, which is what makes the backdrop double as an editor-only visual reference without any editor-specific code.

**Editor-only visual reference backdrop**: each per-map scene has a `Backdrop` `Sprite2D` showing a static 1:1 pixel PNG preview of that map's real tiles, positioned to exactly match the zone rectangle underneath it — so tightening a rectangle in the editor can be done by eye against the real map art, not by guessing coordinates. Rendered by `tools/godot_map_preview.py` (new, in the Godot project's own `tools/`), which replicates `overworld_map.gd`'s `_paint_tiles()` tile-blit logic in PIL: reads `data/maps/<slug>.json` + `assets/tilesets/<tileset>.png`, writes `assets/map_previews/<slug>.png`. Because the backdrop hides itself at real runtime, there's no risk of it ever rendering during actual play.

**Bulk generation**: `tools/generate_encounter_zones.py` (new) carries the same real per-map rate + 10-slot ROM data that previously lived in `EncounterRegistry.OVERRIDES` (transcribed there once already, reused here rather than re-derived) and writes one `.tscn` per map slug, matching a hand-built Route 1 reference file's exact proven structure (`Node2D` root with the container script, a `Backdrop` sprite, one `EncounterZone` child sized to the map's full cell bounds, inline `EncounterSlotData`/`EncounterZoneData` sub-resources). Ran once: **56 zone scenes generated, 0 skipped**, covering every remaining populated map from the `EncounterRegistry` era (Route 1 itself was hand-built first as the proof-of-concept the generator's output is checked against). Deliberately seeded at each map's *full* bounds (matching `EncounterRegistry`'s old `cells: null` behavior, non-regressive) rather than guessed grass/path boundaries — narrowing each rectangle to the real grass extent is explicitly left for the user to do themselves in the editor against the backdrop, per their own stated wish not to need help for this. This also makes the earlier-listed "teach the exporter each tileset's grass tile ID" TODO obsolete — the rectangle-plus-backdrop system solves the same placement problem in a way the user can tune directly, so no tile-ID auto-detection is needed.

**`overworld_map.gd` changes**: `_stitch()` now also calls a new `_spawn_encounter_zones(slug)`, which instances `res://scenes/world/encounter_zones/<slug>.tscn` if it exists, parents it under `_entities`, positions it at that map's real stitched pixel origin, and tags it (`is_encounter_zone_container` meta) for lookup. `encounter_zone_at(cell)` was rewritten to walk tagged containers' `zones()` instead of querying the old registry — same call signature as before, so `player.gd`'s `_check_encounter()` needed no changes at all.

**Verification, two passes**:

Result: **checked 57 of 57 maps, 0 issues found**.

## NPCs get the same treatment: every map with an NPC is now a real, editable Godot scene

**User's own framing, verbatim, is the design brief for this one**: *"scenes dedicated to Pokecenters and Pokemarts for full customization"* and, more broadly, *"if every single zone the player enters could be an entirely editable scene — that would be using Godot to its maximum potential."* Directly continues the encounter-zone pivot above, applied to `NPCRegistry`'s dictionary-override system this time. `NPCRegistry` itself is NOT deleted (unlike `EncounterRegistry`) — it stays as the fallback for any map not yet covered by a generated scene, so nothing regresses while this rolls out.

**`npc.gd` now supports two configuration paths**, chosen automatically per map:
1. **Editor-placed (new default)** — a real `npc.tscn` instance living as a child of a generated `scenes/world/npc_zones/<slug>.tscn`, positioned by dragging it in the 2D viewport against that scene's Backdrop reference image (same convention as `EncounterZone`), configured entirely through its own Inspector fields: `sprite_name`, `text_id`, `npc_id`, and real typed `dialog_data`/`battle_data`/`movement_data`/`reward_data` Resources — the exact same four cookie-cutter resources `NPCRegistry` already used, just attached directly to the node instead of keyed in a Dictionary. `place(map, origin)` derives BOTH the world cell and the world position from the node's own `position` (its LOCAL position within that map, exactly as dragged) — deliberately no separate `cell` field to keep in sync; moving an NPC in the editor is the only "move" operation there is.
2. **Legacy (procedural)** — for any map without a generated scene yet, `overworld_map.gd`'s `_spawn_npcs_legacy()` (the original `_spawn_npcs()`, renamed) still instantiates straight from that map's exported JSON and pulls overrides from `NPCRegistry`, byte-for-byte unchanged. `_spawn_npcs()` is now a two-line dispatcher: use the generated scene if one exists at `scenes/world/npc_zones/<slug>.tscn`, else fall back to the legacy path — so a map is never silently left with no NPCs.

**A real, load-bearing bug fixed along the way, found via the pilot test, not by inspection**: `NPCDialogData.lines`' own doc comment already claimed "one page per entry," but `npc.gd`'s `_as_entries()` tagged every entry `"text"`, not `"para"` — and `dialogue.gd`'s `build_pages()` only hard-breaks a new page on `"para"`, so multiple `lines` entries were actually merging into ONE page (further split only by character budget), contradicting the documented contract. Harmless while `NPCRegistry.OVERRIDES` was empty (nothing exercised a multi-entry `lines` array), but load-bearing now that generated scenes bake real multi-page ROM dialogue into exactly this field — Pallet Town's Girl has 2 real authored pages and both need to actually page-break. Fixed by tagging every entry `"para"` instead, which the pilot test caught directly (asserted `Dialogue._pages.size() >= 2` after `_as_entries()`'s old behavior would have produced 1).

**`_spawn_npc_zone()` reparents each `Npc` out of its loaded container straight into `_entities`, then discards the container** — unlike `_spawn_encounter_zones()`'s container (which stays in the tree, queried live via `global_position`), NPCs are looked up by `npc_at()`/`_npc_occupies()` iterating `_entities`' DIRECT children only, so nesting them under a persistent container would make them invisible to those lookups. Reparenting needed one extra step beyond the obvious `remove_child`/`add_child` pair: Godot warns loudly ("will make owner inconsistent") unless `child.owner` is explicitly cleared first, since `owner` is a separate property from the parent used for scene serialization and doesn't follow a reparent automatically.

**Dialogue resolution is baked in at generation time, not left as a live pointer** — `tools/generate_npc_zones.py` ports `overworld_map.gd`'s `entries_for_text_id()` fuzzy-match and `dialogue.gd`'s `build_pages()` paragraph-grouping (not its character-budget split, which still happens live at runtime same as any other text source) into Python, resolves each NPC's real `TEXT_` constant against that map's own `data/text/<slug>.json`, and writes the resulting real dialogue directly into `dialog_data.lines` as one string per real page. This means whatever the OLD fallback lookup would have shown at runtime is exactly what's now sitting in the Inspector, editable — including its existing warts: Pallet Town's Oak resolves to a short interrupt line ("Stop! Don't- -don't go out!@") rather than his longer "'Tis not safe..." speech, because both text labels fuzzy-match his `TEXT_PALLETTOWN_OAK` id and the shorter one happens to sort first — a pre-existing ambiguity in the matching algorithm, not something this generator introduced, and now directly visible/fixable by hand instead of silently baked into unexamined runtime behavior. An unresolved `text_id` (no fuzzy match at all) is left with empty `dialog_data.lines`, which falls through to the exact same runtime fallback lookup as before — zero regression either way. `battle_data`/`movement_data`/`reward_data` are deliberately left at blank defaults for every generated NPC (no trainer-party data exists in the exported ambient-NPC JSON to seed them from) — authoring one directly in the Inspector is exactly the kind of "adjust/add" work this system exists to enable.

**Scale**: every map with at least one exported NPC got a generated scene — **208 of 221 maps, 917 NPCs total** (the other 13 maps have no NPCs at all, e.g. empty connector rooms). Node names are derived from each NPC's sprite file (`Oak_0`, `Girl_1`, `Nurse_0`, deduplicated on collision) rather than a generic index, so the Scene dock reads as a real cast list per map, not `Node2D_0`/`Node2D_1`.

**A recurring gotcha, now hit a third time this session, for a third asset type**: freshly generated `assets/map_previews/*.png` files (208 of them, one per map, shared naming convention with the encounter-zone backdrops but a fully separate render since NPC-bearing and encounter-bearing map sets don't fully overlap — most indoor maps like Pokémon Centers have no wild encounters at all) failed to load at runtime (`No loader found for resource... expected type: Texture2D`) until one throwaway `godot --headless --editor --quit-after N --path .` pass generated their `.import` files — the exact same "editor hasn't scanned this yet" class of issue previously hit for `class_name` global registration (item 8/architecture-pivot notes). Worth remembering as a general rule now, not a per-asset-type one: **any newly generated file this project's tooling writes directly to disk — a script with a new `class_name`, a new `.png`, likely anything else added outside the editor — needs one editor-mode scan before a plain headless game-mode run can use it**, even though the two runs are otherwise identical from the command line.

**Verification, three passes**:
- `scripts/dev/verify_npc_zones.gd` — deep pilot check on Pallet Town (outdoor, generated scene) and Viridian Pokémon Center (indoor, generated scene): exact npc count, world-cell conversion correct in both the stitched-outdoor case and the origin-zero indoor case, `npc_at()` finds a reparented NPC by cell, a live `interact()` on Girl produces real multi-page dialogue (catching the `para`-tagging bug above), and — critically — a map with NO generated scene (Route 22) still spawns its real NPCs via the untouched legacy path, confirming zero regression for any not-yet-covered map.
- `scripts/dev/verify_all_npc_zones.gd` — structural pass over all 208 generated slugs (enumerated directly from `scenes/world/npc_zones/*.tscn` on disk, not a hardcoded list): spawned NPC count matches that map's real exported JSON count exactly, every `npc_id` is unique within the map, every spawned cell falls inside that map's real bounds, no null `dialog_data`. Result: **checked 208 of 208 maps, 917 total npcs, 0 issues found**.
- A full clean boot (`--headless --quit-after 90`, the user's exact restored autoload list) afterward showed only the pre-existing expected `DevVerify*` fail messages already documented above — no new errors from this change anywhere in the normal boot path.

Both new drivers are dev-only test scripts left on disk, not registered as autoloads in normal play.

**Explicitly not done in this pass, and not needed for the stated ask**: no NPC's rectangle/position was hand-tuned by anyone — every one landed at its real exported ROM cell, which is already correct (unlike the encounter zones, which started at a deliberately-oversized full-map placeholder). What's now possible and open for the user to do directly: drag any NPC to a new spot, add a brand new one by instancing `npc.tscn` into a container, expand `battle_data` to give an ambient NPC a real fight, or edit `dialog_data.lines` to fix a bad fuzzy-match resolution like Oak's — none of that needs another generation pass or a code change.

## The whole map becomes an editable scene: tiles, collision, warps and signs (all 221)

The last step of *"if every single zone the player enters could be an entirely editable scene — that would be using Godot to its maximum potential"* (user, verbatim). The two passes above made a map's NPCs and wild-encounter zones editable; this one makes the map *itself* editable. **The tradeoffs were laid out and the user chose to proceed knowing them** — chiefly that this touches the stitching engine (the most load-bearing part of the port) and that a regeneration overwrites hand edits.

**`MapScene`** (`scripts/world/map_scene.gd`) is one map, as `scenes/world/maps/<slug>.tscn`:
- **Tiles** — a real `TileMapLayer` with that map's real tileset, paintable with Godot's own tilemap editor.
- **Collision** — a *second* `TileMapLayer` at 16px (one tile per CELL, not per 8px tile). **Painted = blocked**, empty = walkable, drawn in translucent red so walls are obvious while editing and hidden automatically at runtime. Chosen over "painted = walkable" because it reads naturally as *drawing walls*.
- **Warps** (`MapWarp`) and **Signs** (`MapSign`) — real draggable nodes whose cell comes from `position`, same convention the NPCs use; target map / target warp number / `text_id` are Inspector fields.
- **connections** — `Array[MapConnectionData]` on the root. **The one field here that isn't safe to freehand**, and it's documented as such in the resource itself: `offset_blocks` is what makes two maps' tiles line up across a seam, measured in BLOCKS (32px), and a wrong value silently shifts an entire neighbouring map rather than erroring.

**The builder runs *inside* Godot, and that was a deliberate reversal of this project's normal generator style.** Every other generator here is Python emitting `.tscn` text. `tools/build_map_scenes.gd` is a headless GDScript `SceneTree` script (`godot --headless --script res://tools/build_map_scenes.gd`) instead, because of `TileMapLayer`'s tile storage: in Godot 4.4 it serialises as `tile_map_data`, a base64 `PackedByteArray` whose layout is an engine implementation detail, not a documented format. Hand-emitting that from Python would mean reverse-engineering a binary encoding with no build-time validation, where one wrong offset yields a silently corrupt map instead of an error. Calling `set_cell()` and letting `ResourceSaver` encode it removes that entire class of risk. (A side lesson: the first inspection looked like a failure because the key was grepped as `tile_data`, its Godot 4.0–4.2 name — the data was there all along under the new name.)

**Two real bugs found and fixed during the build, both of the "compiles and runs fine, silently wrong" kind:**
- **Pathless resources get embedded, not referenced.** `PackedScene.pack()` embeds any resource that has no `resource_path` as a `SubResource` — so the TileSets built with `.new()` were being baked as a private copy into each of the 221 map scenes instead of all of them referencing one shared, separately-editable `.tres`. Fixed by reloading each TileSet from disk after saving it, so the packed scene references the real path. Now 20 shared tileset resources under `resources/tilesets/`.
- **`@onready` is a trap for anything tools or tests instantiate.** `MapScene._collision` was `@onready`, which only resolves when the node enters the tree — so a scene merely `instantiate()`d (exactly what a verifier does, to inspect a map without loading the whole overworld) had a null reference and every `is_walkable_local()` call threw. Replaced with a lazily-cached `get_node_or_null()`. **This also explained an earlier apparent hang**: the flood of error prints from ~94k failing calls, written through a pipe, is what made the first bulk run look frozen — the process was at ~4s CPU and idle, blocked on output, not computing. Worth remembering as a diagnostic: *flat CPU plus no output is a blocked writer, not a slow loop.*

**`overworld_map.gd` changes** — deliberately additive, with the JSON path left intact as a fallback rather than deleted:
- `_stitch()` instances `scenes/world/maps/<slug>.tscn` into a new `$Maps` node at the map's stitched world origin if one exists; otherwise it paints from JSON into the shared `$Tiles` layer exactly as before. **Both paths coexist and interoperate** — verified directly with a scene-based map stitched against a JSON-based neighbour.
- New `_warps_of()` / `_signs_of()` / `_connections_of()` accessors return the *same Dictionary shapes* from either source, so `warp_at()`, `sign_at()`, `_default_spawn()` and `_extend_neighbours()` needed no per-source branching.
- **Warp resolution is now deferred until after the target loads.** Previously `warp_to()` read the destination's warp list out of its JSON up front. That's wrong once warps are draggable: the authoritative copy lives in the target's scene and isn't readable until it's loaded. The warp *number* is now carried across the load in `_pending_warp_number` and resolved in `_spawn_player()` against what the target map actually has. (Cleared on the load-failure path too, so an unresolved number can't leak into the next map.)
- A hard reset now frees `$Maps`' children as well as `$Entities`', and hides them immediately rather than relying on `queue_free()`'s end-of-frame timing — a stale map's tiles would visibly draw under the new one for that frame otherwise.

**Verification, three layers** (a clean run proves nothing here, same discipline as the ROM work):
- **Pilot** (`scripts/dev/verify_map_scenes.gd`): Pallet Town + Red's House 1F, with **every one of Pallet Town's 360 collision cells compared against the exported walkable grid** (not a spot check — this is the one thing that would break movement everywhere), all warps/signs matched field-by-field, editor-only visuals confirmed hidden at runtime, a scene-based map confirmed stitching correctly against a JSON-based neighbour, and a real warp through to the indoor map exercising the new deferred resolution.
- **Bulk** (`scripts/dev/verify_all_map_scenes.gd`): all 221 maps compared against their source JSON — **377,968 tiles (20 deep-checked, one per tileset), 94,492 collision cells, 800 warps, 201 signs → 0 issues**, plus 16 maps loaded live across every tileset → 0 issues.
- **Regression, and this is the one that actually matters for a change this deep**: `verify_full_chain.gd` (cold boot → intro → naming → cultist dream → stairs → front door `LAST_MAP` warp → across Pallet Town → Oak's Lab → starter → rival battle → return) run **twice — once with map scenes active, once with them renamed away to force the legacy JSON path** — and the two outputs are byte-for-byte identical, including the two FAILs, which are therefore **pre-existing and unrelated** (a cultist-dream timing assertion that passes on the very next line, and a lingering `script_active` check). An A/B against the old path was the only way to distinguish "my change broke this" from "this was already failing", since the Godot project isn't under git and there's no other baseline to diff against.

**What this does and doesn't unlock.** Editing tiles/warps/signs/collision on the existing 221 ROM maps now works, and brand-new hand-authored areas are possible for the first time. But the caveat from the pre-decision tradeoff discussion stands and is worth restating: **`build_map_scenes.gd` overwrites wholesale**, so a rebuild discards hand edits. It takes explicit slugs (`-- pallet_town route1`) precisely so the blast radius can be limited when the upstream export genuinely changes. There is no merge strategy yet; that's the main open risk of this design.

## Two real bugs, both from actually using the new systems: game wouldn't launch, and hand-tuned encounter zones stopped triggering

**The game wouldn't start at all.** Reported as "the game is not running" — every launch attempt closed within about a second. Root cause: `project.godot`'s autoload list still had 6 leftover one-shot test harnesses (`DevVerifyWorld`, `DevVerifyWarps`, `DevVerifyIntro`, `DevVerifyOaksLab`, `DevVerifyTextEngine`, `VerifyPlayerFacing`) that got re-added during earlier Project Settings exploration this session. Every one of them ends in `get_tree().quit()` and was written assuming `main_scene` points directly at whatever it tests — not at the real boot flow. With `main_scene` correctly pointed at the Gothic intro, each one woke up ~0.3s after launch, saw the current scene was `"GothicIntro"` instead of the `"Overworld"` it expected, printed a FAIL, and force-quit. Confirmed directly from the user's own recent `AppData/Roaming/Godot/app_userdata/PokemonPurple/logs/*.log` files, all showing the identical `FAIL: current scene is 'GothicIntro', not Overworld` pattern. Fixed by removing all 6 from `project.godot`; a real boot now runs clean (`EXIT=0`, no forced quit) instead of dying immediately. **Lesson for this project specifically**: any dev-verify script meant to run standalone should never be left as a permanent autoload — it's fine as a *temporary* one for an isolated test (this session does that constantly, always restoring the real list after), but if one lingers past its test run it silently breaks the actual game the next time anyone just tries to play it.

**Hand-tuned encounter zones stopped triggering.** The user started shaping Route 1's real grass extent in the editor per the earlier "tighten the placeholder rectangles yourself" note — but since Route 1's grass isn't one clean rectangle (broken up by the path/trees), they did the natural thing and added 7 more `CollisionShape2D` siblings under the zone's `Area2D` to compose the real shape out of several rectangles. `EncounterZone.gd`, though, had `@onready var _shape: CollisionShape2D = $CollisionShape2D` — a single hardcoded lookup by node name, matching only the first shape. Every rectangle added after that was silently never consulted, so any cell only covered by one of the new shapes read as outside the zone, and wild encounters stopped triggering there. **Not a one-off Route 1 quirk — every zone is expected to end up shaped this way**, per explicit user correction ("it will never be just one square"), so the fix is a real generalization, not a special case: `get_cell_rects()` now walks every direct `CollisionShape2D` child with a `RectangleShape2D` and returns all of them; `contains_cell()` checks all of them; `get_cell_rect()` (singular) is kept only for old callers that still want one representative rect. Verified live: loaded Route 1, found a real walkable cell covered only by one of the 7 added shapes (not the original), confirmed `contains_cell()` now returns true for it, and rolled a real wild encounter (HOPPIP Lv3) from that exact cell.

**Two dev-verify scripts had baked-in single-rectangle assumptions from when every zone was still a generated placeholder** — `verify_all_zones.gd` asserted a zone's rect exactly matched the full map bounds (now false for any hand-split zone), and `verify_zone_scene.gd` hardcoded specific "inside"/"outside" test cells against Route 1's original single rectangle (now meaningless coordinates for a differently-shaped zone). Both rewritten to be shape-count-agnostic: the bulk check now verifies every shape is non-degenerate and stays within its map's bounds rather than comparing to full-map dimensions; the pilot check derives its "a real cell inside the zone" test point from whatever the zone's own first shape actually is, rather than a hardcoded coordinate. Both re-verified passing (57/57, and the Route 1 pilot) after the rewrite — this is the same "a test written for one generation-time snapshot goes stale the moment the content it checks is real, hand-edited content" lesson as the NPC dialogue system's `_as_entries()` para-fix earlier, applied to a different subsystem.

## Experience system: real Gen 1 growth curves, level-up, move learning

Status check before starting: Party Menu already had a real working START → party list → status screen. Inventory was (and still is) just `GameState.items`/`money` with no UI or use-item logic. Experience didn't exist at all — no `exp` field on `PartyMon`, nothing granted on a battle win, no level-up trigger. User picked Experience first, since it's self-contained (no dependency on the other two) and everything else already assumes it exists.

**Formulas verified against this ROM's own source, not general Pokémon-series knowledge** (a dedicated research pass read `engine/pokemon/experience.asm`/`data/growth_rates.asm` and `engine/battle/experience.asm` directly): the exp-to-level curve is `EXP(n) = ([1]/[2])·n³ + [3]·n² + [4]·n − [5]` per growth-rate group, all 6 ROM groups implemented in `PartyMon.exp_for_level()` (`GROWTH_MEDIUM_FAST`/`_FAST`/`_SLOW` are simple cubics; `_MEDIUM_SLOW` has the extra quadratic/linear terms; `_SLIGHTLY_FAST`/`_SLIGHTLY_SLOW` exist in the ROM's constant table but no species in this game's 240-strong roster actually uses either — implemented anyway for exactness). Battle exp gain is `BattleMath.calc_exp_gain()`: `floor(base_exp · enemy_level / 7)`, ×1.5 (also truncating) for a trainer battle. Deliberately NOT implemented: the ROM's traded-Pokémon 1.5x boost (no trading system exists in this port) and its divide-by-participant-count split (this port's battle engine only ever has one active mon per side, so there's never more than one participant — noted directly in the code as the thing that has to change FIRST, before the exp formula itself, if multi-mon battles are ever added).

**`PartyMon.gain_exp(amount)`** applies level-ups one at a time, not jumping straight to the final level from a big gain — this matters because it means a move-learn check fires at *every* level threshold actually crossed in a single win, matching `GainExperience`'s own sequential processing rather than an after-the-fact "what would this mon know now" reconstruction. Each level-up carries the *gained* max HP into `current_hp` (`current_hp += new_max − old_max`), not a full heal — matches `CalcStats` being invoked mid-level-up in the ROM. A move learned while already at 4 known moves bumps the *oldest* one, same convention `_initial_moveset()` already used for a freshly-created mon; there's no interactive "forget a move?" prompt yet (the real games ask; this port has no UI for that built). A dead (permadeath) mon is a hard no-op — exp for a mon that's already gone is never correct.

**A real bug caught before it shipped, not after**: the first draft returned `learned_moves`/`forgot_moves` as two separately-indexed arrays. That's wrong the moment a single level-up both fills an open move slot *and* bumps an old one in the same pass — the two arrays would desync and the battle log would pair the wrong forgotten move with the wrong learned one. Fixed by returning one array of `{"move": ..., "forgot": ...}` entries instead, each learn event carrying its own forget (or none) inline — no index correspondence to maintain at all.

**Verification, two layers**:
- `scripts/dev/verify_experience.gd` — the curves checked against real, independently-known Gen 1 level-100 totals (800,000 / 1,000,000 / 1,059,860 / 1,250,000 for FAST/MEDIUM_FAST/MEDIUM_SLOW/SLOW), `level_for_exp` confirmed as an exact inverse, the exp-gain formula hand-computed and checked (`floor(64·10/7)=91` wild, `floor(91·1.5)=136` trainer), a full *real* battle fought via the actual `Battle` controller (not a mocked shortcut) with the resulting exp gain checked against the exact expected amount, and an isolated `gain_exp()` call targeting EEVEE's real level-27 learnset entry (QUICK_ATTACK — chosen specifically because CLAUDE.md documents Eevee's next learnset move after level 1 isn't until 27, so an earlier target level would have silently never exercised the move-learn/bump path at all) confirming the exact move learned, the exact move forgotten, and the exact HP carried forward.
- `test_battle.gd`, the pre-existing battle regression suite, re-run afterward with no changes needed — full pass, confirming the exp hook didn't disturb turn order, status effects, or the existing win/loss detection.

**A real bug in my own test, not the game, worth remembering**: the first version of the live-battle test used a bare `var ended := false` captured by a signal-connected lambda (`func(_r): ended = true`), and the loop kept spinning past 30 turns even though the exp assertion right after it proved the battle really had ended correctly. GDScript lambdas capture outer **local** variables **by value** at closure-creation time, not by reference — `ended = true` inside the closure was writing to the closure's own private snapshot, never the loop's variable. Fixed by capturing a one-element `Array` instead (`[false]`) and mutating index 0 — Arrays are reference types, so the same underlying object is visible on both sides. Worth remembering generally: any dev-verify script that needs a signal callback to flip a bare local bool/int for a `while` loop to observe needs this same wrapper, not just this one test.

**A real, reproducible-but-unrelated test failure chased down and ruled out, not ignored**: right after this work, `verify_full_chain.gd` (the full boot→rival-battle regression) started failing at the "exit Red's House's front door" step — the player got stuck, unable to move in any of the 4 directions, from the exact same cell, 3 runs in a row. Since none of the 3 files this work touched (`party_mon.gd`, `battle.gd`, `battle_math.gd`) have any code path connected to overworld movement or warping, this got a real investigation rather than a shrug: a direct `is_walkable()`/`can_enter()` check at the stuck cell came back `true` for every neighbor, and manually driving the player there via a plain `load_map()` (not a real warp) moved it just fine — proving collision/movement themselves were never broken. Reproducing the REAL path (a real `warp_to()`, matching the stairs, not a direct `load_map()`) revealed the actual state: `Dialogue.is_active` and `GameState.script_active` were both `true` at the exact moment the test tried to walk — a real, correctly-functioning input gate (the same one `player.gd`'s `_process()` has always checked), not a movement bug at all. Something is auto-triggering dialogue on arrival at Red's House 1F that `verify_full_chain.gd`'s own hardcoded step sequence has never explicitly accounted for or waited out, coincidentally timing-dependent enough to usually go unnoticed. This traces back to the exact same family as the already-documented "cultist dream auto-started" flake earlier in this same test (previously confirmed, via a byte-identical A/B run, to be pre-existing and unrelated to whatever was being changed at the time) — not a new problem, just a second symptom of the same underlying test fragility. **Left unfixed for now** (out of scope for an experience-system pass), but the investigation itself is worth keeping: it's the difference between "my change might have broken movement, better dig in" and correctly concluding "verified this isn't that."

## Inventory system: real ROM item data, a Bag menu, and permadeath-safe item-use effects

Second of the three systems the user picked (Party Menu / Inventory / Experience), in the order they chose: Experience first (done above, self-contained), then Inventory. Party Menu's own missing piece (using an item on a mon) was explicitly blocked on this existing first — this pass closes that gap directly, extending the existing Start-menu overlay rather than building a parallel UI.

**Every real ROM item, not a hand-picked subset** — `tools/generate_items_json.py` parses `constants/item_constants.asm` (the ordered name list, 83 real items before the elevator-floor-ID overload begins), `data/items/prices.asm`, `data/items/names.asm`, and `data/items/key_items.asm` directly, all four positionally zipped (they share the exact same per-item order in the ROM). Real numbers, not approximated: POTION $300/20 HP, FULL_RESTORE $3000, REVIVE $1500, MASTER_BALL unbuyable ($0), sell price confirmed as always exactly half of buy (verified in `engine/events/pokemart.asm`, not assumed from general series knowledge). **One deliberate, documented exception to "parse the table, don't hand-transcribe"**: an item's actual *effect* is CODE in Gen 1 (`engine/items/item_effects.asm`'s per-item jump table), not a data table — there's nothing to mechanically parse. The generator's `EFFECTS` dict hand-encodes this piece specifically, transcribed from a direct read of that file, with its own header explaining exactly why this one field can't be automated like the other three. `ItemData` (new Resource, mirroring `PokemonSpecies`/`MoveData`) carries the result; `tools/generate_item_resources.gd` turns the JSON into 83 real `.tres` files the same way species/moves already work, and `GameData.get_item()` joins `get_species()`/`get_move()` as a third parallel lookup.

**Effect logic lives on `PartyMon.use_item(item)`**, mirroring `gain_exp()`'s own shape (a Dictionary result the caller narrates from, not a bare bool) — `HEAL`/`HEAL_FULL`/`HEAL_FULL_STATUS` (Full Restore's real effect: heals to full **and** cures status in one use, succeeds if *either* was needed, not just when both apply), `CURE_STATUS`/`CURE_ALL_STATUS`, `REVIVE_HALF`/`REVIVE_FULL`. **The one rule that actually matters in this fork**: every healing path checks `is_dead` first and refuses outright — not just Revive/Max Revive, a plain Potion too, since a permadeath-dead mon can't be healed by anything, full stop (CLAUDE.md item 1). Worth being explicit about what that means in practice: since `current_hp` reaching 0 and `is_dead` becoming `true` happen in the exact same synchronous step in `battle.gd`'s `_check_faint()`, there is no real "fainted but not yet dead" state in this game for Revive to ever legitimately catch — Revive/Max Revive can **never actually succeed** here. Implemented as a real `is_dead` check anyway (not a hardcoded always-fail), both because that's what's honestly correct and because the isolated test suite proves the fainted-but-hypothetically-not-dead code path still works right, in case that invariant ever changes. A no-effect use (full HP already, wrong status for that specific cure item, item has no real effect at all) reports failure and — this is the part that had to be gotten right at the call site, not just the mon — **never consumes the item**, matching the real games.

## Poké Ball catching: the real Gen 1 formula, ported line-for-line, plus a real battle-scene ITEM menu

The last of the three "natural extension" items left over from Inventory (Poké Ball catching, Escape Rope/Repel, TM/HM use) — picked over the other two since it needed no new subsystem (no overworld step-counting), just a wild-battle-context item action the battle scene didn't have yet.

**The catch formula is `engine/items/item_effects.asm`'s `ItemUseBall`, read directly and ported line-for-line into `BattleMath.attempt_catch()`** — not a general "Gen 1 catch rate" formula recalled from memory. Real Rand1 ranges per ball (any [0,255] for a Poké Ball, re-rolled until ≤200 for Great Ball, ≤150 for Ultra/Safari), the real status-ailment subtraction (12 for burn/paralysis/poison, 25 for freeze/sleep, an outright guaranteed catch if it underflows past Rand1), the real two-stage HP/catch-rate calculation (`W = floor(floor(MaxHP·255/BallFactor) / max(floor(HP/4),1))`, BallFactor 8 for Great Ball else 12, capped at 255 as `X`; a straight `catch_rate < Rand1` check; an outright capture if the *pre-cap* `W` exceeds 255; otherwise a second roll against `X`), and the real, separate miss-shake calculation (`Z = floor(X·Y/255) + Status2`, `Y = floor(catch_rate·100/BallFactor2)`, thresholds at 10/30/70 for 0/1/2/3 shakes) used only to pick which of the 4 real miss messages to show. GDScript's plain integer division is floor division for positive operands, same as the Z80's, so every intermediate step ports directly with no emulation quirks to work around.

**This fork's hidden tier system (CLAUDE.md item 5) does NOT feed into catch odds — confirmed by reading the actual WRAM struct layout, not assumed.** `ram/wram.asm` shows `wEnemyMonActualCatchRate` sitting immediately after `wEnemyMonBaseStats`, populated straight from `BaseStats` during battle setup (`LoadEnemyMonData`'s `wMonHCatchRate → wEnemyMonBaseStats+N` copy) — a value this fork deliberately keeps separate from `wEnemyMonCatchRate`, which it repurposes to hold the enemy's *rolled tier* instead (confirmed at the exact WRAM byte this fork overwrites with a tier roll, just above the real catch-rate copy in the same function). No UI reads `box` yet; that's the one deliberately deferred piece.

Trainer battles block the throw outright (`is_trainer` gate, checked before any catch math runs) with the real ROM message ("You can't catch another TRAINER's POKéMON!") — and, correctly, the ball is *not* consumed in that case, since nothing was actually thrown; consumption happens at the battle-scene call site, gated on `not result.blocked`, not unconditionally.

## Fixed: `SceneFlow.continue_game()`'s `pending_spawn`-ordering bug (the one flagged, not-yet-fixed item from `BattleLauncher.fight()`'s own regression)

Picked as the "quick, already-diagnosed, low-risk" item over the two remaining feature gaps (PC Box, TM/HM) — a real bug already root-caused once elsewhere in this exact codebase, not new design work.

**Same underlying bug as `BattleLauncher.fight()`'s own "doesn't stay in the same spot" fix, just in a second call site that was never touched the first time.** `Overworld._ready()` unconditionally auto-loads its own design-time default `map_slug` ("pallet_town") the instant the scene is instantiated, and that auto-load's `_spawn_player()` reads-and-RESETS `GameState.pending_spawn` as a side effect, regardless of what it holds at the time. `continue_game()` was setting `pending_spawn`/`pending_facing` to the real saved position *before* calling `_change()` (itself a `call_deferred` to `_do_change()`) — meaning the real saved values sat in `GameState` for the entire stretch between that assignment and the scene swap actually happening, getting silently eaten by the auto-load's own reset before `_do_change()`'s explicit `load_map()` call ever ran. A player choosing CONTINUE landed on whatever map they saved in, but always at that map's generic default spawn point, never their actual last-stood tile.

**The fix moves the assignment to *inside* `_do_change()`, after the scene swap and immediately before the explicit `load_map()` call** — exactly the ordering `BattleLauncher.fight()` already proved correct, now applied here too. `_change()`/`_do_change()` gained two new parameters (`spawn_cell`, `spawn_facing`, defaulting to `(-1,-1)`/`"down"`) so `continue_game()` can thread its saved position through the deferred call instead of setting `GameState` directly beforehand; `naming_done()` (the other caller) needed no changes — its own prior explicit `pending_spawn = Vector2i(-1,-1)` was already identical to the new default, so the refactor is a no-op for it in practice, and it now benefits from the same safe ordering by construction rather than by coincidence.

**A second, genuinely distinct bug surfaced *while verifying* the first fix, in the exact same function — worth its own entry, since it looked identical but wasn't.** The first attempt at this fix (correct in principle) still failed a live save/CONTINUE round-trip test: the player landed back at the map's default spawn regardless. Direct instrumentation (`Engine.get_process_frames()` + instance IDs printed at every `_spawn_player()` call and at both ends of `_do_change()`'s `await`s — the same "don't trust a clean run, go observe the live state" approach this whole project leans on) showed the real sequence: `change_scene_to_file()`'s actual scene swap (freeing the old scene, instantiating the new one, running its `_ready()` — including the OWN auto-load `_spawn_player()` call) happens within essentially the same frame as the call itself, not deferred to "the next frame" the way a single subsequent `await get_tree().process_frame` assumes. With only one await, `_do_change()`'s own `root := get_tree().current_scene` read was still resolving too early relative to that swap in some runs. `BattleLauncher.fight()` already awaits `tree.process_frame` **twice** after its own `change_scene_to_file()` call, for this exact reason — `_do_change()` only had one. Added the second await to match.

**Even with the timing correctly matched to `BattleLauncher.fight()`'s own proven pattern, the very same live test still failed on the first re-run — and this time the bug was in the *test*, not the fix.** More instrumentation showed the fix was actually working correctly: the auto-load's own default-spawn placement is a real, unavoidable transient (the new scene's `_ready()` fires and spawns a player at the generic default *before* `_do_change()`'s own pending coroutine resumes and re-loads with the correct saved position, a harmless couple-of-frames flicker no real player would ever notice) — but the test's polling loop stopped and asserted the instant *any* player node existed, reading that transient default-spawn state as if it were final, before the corrective reload ever got a chance to land. Fixed by polling for the player actually being *at the saved cell* (with a generous timeout), not just "a player exists" — after which the exact same fix passed cleanly with no further changes.

**Verification, `scripts/dev/verify_scene_flow_continue.gd`**: loads Pallet Town for real, places the player at a genuine, walkable, non-default cell (found by scanning outward from `_default_spawn()`'s own computed value and confirming it differs), sets a distinct facing, calls the real `SaveSystem.save_game()`, then drives `SceneFlow.continue_game()` exactly as `main_menu.gd`'s CONTINUE option would. Confirms the restored player lands on the exact saved cell and facing — not the map's default spawn — and on the exact saved map. All 9 assertions pass. `verify_full_chain.gd` (a `new_game()` path, the other real caller of the shared `_change()`/`_do_change()` code) re-run afterward with no change in outcome, confirming the shared-helper refactor didn't disturb the boot flow it already covers.

## Cookie-cutter trainer sight/chase system: every trainer NPC can notice the player, walk up, and start a real battle — the same way Gen 1 actually does it

Explicit user request, scoped as "a HUGE part of the game… perfect, efficient, cookie cutter… a Pokémon game editor" — every NPC gets a real, per-instance on/off switch for this, not a hand-scripted special case per trainer.

**Derived from the real ROM mechanic, not designed from scratch.** `engine/overworld/trainer_sight.asm` (`CheckSpriteCanSeePlayer`/`CheckPlayerIsInFrontOfSprite`) and `home/trainers.asm` (`CheckFightingMapTrainers`/`TalkToTrainer`/`StartTrainerBattle`/`EndTrainerBattle`) were read directly to confirm the real rules rather than assumed: same row/column as the player, within the trainer's own `view_range` (a per-trainer field in the map's own `trainer` header table, `scripts/<Map>.asm` — **not** part of `object_event`'s data at all), the player standing in front of the trainer's facing direction, and deliberately **no line-of-sight/obstacle/tall-grass check** — pure coordinate math, confirmed by reading the routine and preserved as-is rather than "fixed." An exclamation bubble shows for exactly 60 ROM frames (`engine/overworld/emotion_bubbles.asm`'s own `DelayFrames` call) = 1 real second at 60Hz. The trainer then walks straight along **its own facing axis only** (`TrainerWalkUpToPlayer` never turns a corner or re-aims mid-walk) and stops exactly one tile short of the player. A win sets the trainer's own `EVENT_BEAT_<MAP>_TRAINER_<N>` flag permanently and calls `HideObject` on their overworld sprite — no rematches, ever, in Gen 1 — and pays `base_money(trainer_class) × enemy's last-or-only mon's level`, confirmed from `engine/battle/read_trainer_party.asm`'s real `wAmountMoneyWon` BCD-add loop rather than recalled from memory. A loss is identical to a plain wild-encounter blackout — no trainer-specific text, no flag set, so a lost fight can be retried. View range 0 (gym leaders, Elite Four, the rival's Oak's Lab fight) is the real ROM's way of saying "mathematically un-spottable by sight, this one is scripted" — those bosses keep their existing custom map-script battle flow untouched and simply never get sight data at all.

**Correlating an `object_event`'s trainer to its real header required a real lookup, not an ordinal shortcut**: `object_event`'s trailing `(OPP_CLASS, trainer_set)` pair (8-argument form — the "is this a trainer" signal is the argument count itself, not a visible flag) only gives species/level via `data/trainers/parties.asm`. `view_range`/`event_flag`/pre-post battle text live in a completely separate per-map `trainer` header table with no positional relationship to `object_event`'s own ordering. `parse_trainer_headers()` (new, `tools/godot_export.py`) bridges the two the same way the game itself does: the object's `text_id` → the map's own `TextPointers` table → that label's own script body → the `ld hl, <Map>TrainerHeaderN` line inside it → the real header entry.

**Extension summary, each piece cookie-cutter across every NPC in the game:**
- **`tools/godot_export.py`**: `parse_trainer_headers()` (header/flag/sight-range/text-label resolution above), `trainer_parties()`/`trainer_base_money()` (self-contained `parties.asm`/`pic_pointers_money.asm` parsers, matching this project's "each tool is standalone" convention rather than importing `godot_export_data.py`), and `parse_objects()` extended to resolve `facing` for every NPC (not just trainers) plus `is_trainer`/`trainer_class`/`party`/`reward_money`/`sight_range`/`defeated_flag`/`challenge_lines`/`defeat_lines` for the trainer ones. Verified directly against Route 3 (all 8 trainers resolved correctly) and Cerulean Gym (2 regular trainers fully resolved, Misty correctly missing `sight_range`/`defeated_flag` since her fight is custom-scripted, not generic).
- **`NPCSightData`** (`scripts/resources/npc_sight_data.gd`, new): just `enabled: bool` + `sight_range: int` — the per-NPC on/off switch the user asked for, editable straight in the Inspector like every other cookie-cutter data resource (`NPCDialogData`/`NPCBattleData`/`NPCMovementData`/`NPCRewardData`). `sight_data.enabled == false` doubles as both "ambient NPC, no sight system at all" and the real ROM's own "view range 0" boss case.
- **`npc.gd`**: `check_sight(player_cell)` — called once per completed player step (not polled every frame; the real routine only ever succeeds right as a step completes anyway, so per-step is cheaper without changing when it can fire), same-row/column-and-in-front alignment math, deliberately no obstacle check, matching the ROM exactly. `_engage_sight(distance)` shows the new `ExclamationLabel` child node for 1 real second, walks the trainer along its own facing axis `distance - 1` steps, then hands off to the existing `BattleLauncher.run_npc_battle()` — the same function a direct player-initiated `interact()` battle already uses, so reward/flag/permanent-hide-on-win all just work with no separate code path to keep in sync. `_hide_forever_if_already_defeated()` (called from both `setup()` and `place()`) `queue_free()`s a defeated trainer's node outright rather than just hiding it — real Gen 1 behavior (`HideObject`), and it gets `npc_at()`/occupancy checks correct for free since a freed node simply isn't there to match against.
- **`overworld_map.gd`**: `_check_trainer_sight(world_cell)`, called from the tail of `on_player_moved()`, scans every loaded entity and calls `check_sight()` on each — the one line that actually wires the per-NPC mechanism into real player movement.
- **`tools/generate_npc_zones.py`**: `build_tscn()` now bakes real `facing`, and for trainer NPCs with a resolved party, real `battle_data` (party/challenge_lines/defeat_lines), `reward_data` (real money), and — only when `sight_range > 0` — `sight_data`. Also made Pillow genuinely optional (`render_preview()` falls back to reusing an existing preview PNG when unavailable) since this session's Python has no PIL/pip — a real, permanent tool improvement, not a one-off workaround.

**Real bug caught, not just a possibility flagged: `PSYCHIC_TR` → `_class_key()`'s naive transform produced `"PsychicTr"`, but the real party-data label in `data/trainers/parties.asm` is just `PsychicData` (no "Tr").** `constants/trainer_constants.asm`'s `trainer_const PSYCHIC_TR` is disambiguated from the unrelated Pokémon-type constant `PSYCHIC` — trainer classes and move/type constants share one C-style namespace in this codebase — but that disambiguation was never carried into the party-data label itself, since nothing else needs to distinguish them there. Silent, not a build error: `trainer_parties().get("PsychicTr")` just returned nothing, so all 4 of Saffron Gym's `PsychicTr`-class Youngsters (trainer_set 1–4) exported with an empty `party`, which cascaded into empty `battle_data` **and** no `sight_data` at all in the generated scene (`build_tscn()` gates `sight_data` on a non-empty resolved `party`). Caught by a structural cross-check comparing every regenerated scene's real `battle_data`/`sight_data` node counts (330/291) against the exported JSON's own trainer/sight totals (334/295) — a 4-trainer, 4-sight-data gap that didn't show up in any single-map pilot test (Route 3, Cerulean Gym) since neither happens to use this trainer class. Traced to the exact mismatch by grepping `constants/trainer_constants.asm` for `PSYCHIC` and `parties.asm` for `^Psychic`, and cross-checked against every other `trainer_const` entry the same way to rule out a second mismatch (one false-positive turned up, `'Const'`, which was the diagnostic script's own regex matching across the `MACRO trainer_const` definition's line break — not a real trainer class at all). Fixed with a small, explicit `_CLASS_KEY_OVERRIDES` dict checked before the naive transform (documented in-line with the reasoning above, so a future second exception is easy to add the same way) rather than special-casing the lookup itself. Re-running the full export + `generate_npc_zones.py` afterward brought every count to an exact match: 334/334 trainers, 295/295 with sight data, zero empty parties.

**Verification, two layers** (`scripts/dev/verify_trainer_sight.gd`, left on disk per this project's convention of keeping dev-verify scripts around unregistered): an **isolated** synthetic-NPC test on Pallet Town (decoupled from any one map's real layout — a fresh `NPCSightData`/`NPCBattleData`/`NPCRewardData` per instance, not the shared defaults baked into `npc.tscn`, which would otherwise corrupt state across multiple hand-built test instances) proving out-of-range/misaligned rejection, the bubble timing, the one-tile-short walk-up, a real battle triggering, real money awarded, the permanent defeated flag, and `GameState.script_active` clearing correctly at the end — `run_npc_battle` shows a real dialogue the player must dismiss both before *and* after the fight, and `fight()` itself swaps the scene back to Overworld before that trailing dialogue resolves, so the test waits on `not GameState.script_active` rather than on the scene name, which stops tapping too early otherwise. A **live** test against Route 3's real `route3#4` (a real WEEDLE Lv9 BugCatcher, `sight_range=1`) proves the real exported data drives real gameplay end to end, including `base_money(BugCatcher)=1000 × 9 = 9000` and the trainer's sprite being gone for good after a fresh map reload. All 23 assertions pass.
