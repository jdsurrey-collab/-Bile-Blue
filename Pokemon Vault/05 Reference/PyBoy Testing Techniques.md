# PyBoy Testing Techniques

## Why this exists
This working environment has no interactive Game Boy emulator. A clean `make -Weverything` only proves the code *assembles* — it has caught **zero** behavioral bugs this entire project. Every real bug documented across [[Cultist Dream Sequence]], [[SGB Colorization Cleanup]], and [[Smarter Trainer AI]] was found by actually running the built ROM in a headless emulator and reading its live state directly, not by re-reading the source more carefully.

## Setup
```sh
python3 -m venv /root/pyboy-env
/root/pyboy-env/bin/pip install pyboy Pillow
```
(Needs `python3-pip`/`python3-venv` via `apt-get install`.) `pokered.sym` — regenerated by every `make` — provides the bank:address pairs needed to hook or jump to any labeled function.

## Core techniques

### Hooking a function's entry point
```python
pyboy.hook_register(bank, addr, callback, context)
```
Fires `callback` every time the CPU executes that address. Inside the callback, `pyboy.register_file.A/B/C/.../HL/PC` reads live CPU registers — this is what caught the `farcall` register-clobber bug in [[Cultist Dream Sequence]] (no amount of re-reading the source found it; direct register inspection did, on the first attempt).
**Caveat:** hooks patch the target instruction with a special opcode — hooking mid-function rather than at a clean entry point can corrupt execution (discovered hooking `ReadMove` mid-function once).

### Reading/writing memory directly
`pyboy.memory[addr]` reads/writes WRAM/HRAM/ROM directly (addresses from `.sym`). Used to confirm tile fill values, WRAM scratch state, etc.

### Screenshotting
`pyboy.screen.image.save(path)` dumps the current frame as a PNG. **Renders plain DMG grayscale — no SGB colorization support at all** — a screenshot never proves an SGB palette edit did what was intended, only that the ROM boots/runs.

### Input
`pyboy.button("a", hold_frames)` queues a press auto-released after that many `pyboy.tick()` calls. The naming screen can be skipped instantly with `start` (`.pressedStart` submits immediately even with an empty name) rather than navigating the letter grid.

### Tile-content verification (not layout reasoning)
Don't reason about VRAM layout/unions from source alone. Read `rLCDC` (`pyboy.memory[0xff40]`) to get the real tile-addressing mode: bit 4 clear = signed "$8800 method" (base `$9000`, tile ID as signed byte); bit 4 set = unsigned "$8000 method" (base `$8000`). Compute the real address for the tile ID in question and read those 16 bytes directly. This caught the `ClearScreen` fill-tile bug that static VRAM-layout analysis got wrong on the first pass.

### A WRAM value can look plausible before real game state is actually live
A map's WRAM state (e.g. `wCurMap`) can read as a plausible-looking value *before* the real game state is actually live — caught a false-positive "arrived in the target room" read this way. A hook firing on a specific script/function's own entry point is a far more reliable "have we actually gotten here" signal than polling a WRAM value.

## Direct-function-call harness (unit-testing a single Z80 function)
Reusable pattern, built for and proven on [[Smarter Trainer AI]]:

1. Push a "trampoline" return address (an infinite `jr -2` = bytes `0x18 0xFE`, written into unused scratch WRAM) onto the stack by hand:
   ```python
   sp = (pyboy.register_file.SP - 2) & 0xFFFF
   # write trampoline address little-endian at sp
   pyboy.register_file.SP = sp
   ```
2. Set input registers, set `register_file.PC` to the target function's address (from `.sym`).
3. `tick()` in a loop until `register_file.PC` returns to the trampoline address — output registers/WRAM can then be read directly.

This is effectively a unit test for a single Z80 function, no need to play through to a real battle.

**Note:** only `HL` is a valid combined-register property on `register_file` — `DE`/`BC` aren't settable/gettable as pairs; use individual `D`/`E`/`B`/`C`.

### Two environment prerequisites, discovered the hard way
- **The Nintendo boot ROM overlay is still mapped over `0x0000-0x00FF`** immediately after `PyBoy(...)` construction — nothing has run the real boot sequence far enough to disable it. Any function living in that range (e.g. `CopyData` at `0x00b5` in this build) silently executes stale boot ROM bytes instead of real cartridge code — not a crash, just wrong instructions, which looks exactly like a hang or a jump into garbage.
  **Fix:** `pyboy.memory[0xFF50] = 1` once, immediately after construction, before any other setup.
  > ⚠️ **Correction — this poke is ONLY for the no-boot case.** It applies when you jump straight to a target function *without* booting. If your harness also ticks frames to boot the game (which you want whenever the function under test depends on real initialized WRAM/HRAM), poking `0xFF50` up front unmaps the boot ROM *while the CPU is still executing inside it*, crashing into cartridge ROM before your test runs. Signature: `PC` parked at `$0038` (an `rst` vector — the classic "executing `$FF` filler" crash) and `SP` wandered out of WRAM into cart-RAM (`$a290` observed), **before** the forced `PC` jump. It presents as "my function times out" — identical to a real bug in the function, so it's easy to misattribute (it produced 6 bogus failures during the [[Species Index Ceiling - GetName Fix]] work).
  > **If you boot at all, don't poke `0xFF50`** — the boot ROM unmaps itself on the way out, leaving real cartridge code at `0x0000-0x00FF` anyway (verified: `0x00b5` reads the real `CopyData` bytes `2a 12 13 0b 79 b0 20 f8`), plus a sane stack (`SP=$dfe9`) and bank.
  > **Cheap guard worth keeping in every harness:** `assert SP > 0xC000` right after boot, so a crashed boot fails loudly and immediately instead of masquerading as a failing function.
- **Calling into a non-zero bank needs BOTH `pyboy.memory[0x2000] = bank`** (the real MBC bank-select register write) **AND `pyboy.memory[hLoadedROMBank] = bank`** (the game's own HRAM shadow, read by `homecall`/`Bankswitch` to know what to restore afterward) — if the target function (or anything it calls) uses `homecall`/`farcall`/`callfar` internally (e.g. `Divide` homecalls into a separate bank). Skipping the `hLoadedROMBank` write causes the bank to be restored to something wrong mid-call, and execution wanders into unrelated code — which looks exactly like a bug in the target function from the outside, and cost significant debugging time before being identified.
