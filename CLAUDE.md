# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project scope

This is **Pokémon Purple**, a grimdark, gritty, Victorian-gothic reimagining of Pokémon Red/Blue, forked from the [pret/pokered](https://github.com/pret/pokered) disassembly. Ten things distinguish it from vanilla pokered:

1. **Hardcore permadeath mode**: a Pokémon that faints in battle is permanently marked dead (bit 7 of `MON_STATUS`, unused by vanilla status ailments — see `constants/battle_constants.asm`'s `DEAD_BIT`). Dead Pokémon can never be revived (Pokémon Center, Revive, Max Revive all check the flag) and show `RIP` instead of `FNT` in the party screen (`home/pokemon.asm`). The player's own blackout behavior is untouched — whiting out still just returns you to the last Pokémon Center as in vanilla.
2. **Victorian-gothic story rewrite**: every NPC/sign/menu text in `text/*.asm` (plus the opening monologue in `data/text/text_2.asm`) has been rewritten in a darker, Victorian register (archaic diction, mourning/funeral imagery, class-conscious cruelty), each location given its own unique despair-flavored treatment while preserving the original substance. Each Gym Leader carries a distinct thematic flavor (Brock=stone/tomb, Misty=drowning, Surge=war veteran, Erika=beauty-and-rot, Koga=plague, Sabrina=madness, Blaine=ash/ruin, Giovanni=cold menace).
3. **Single merged ROM, no version exclusives**: this fork only builds one ROM (`pokered.gbc`; the `_BLUE` build path has been removed from the Makefile). All wild-encounter tables in `data/wild/maps/*.asm` that used to branch on `IF DEF(_RED)`/`IF DEF(_BLUE)` (Oddish/Bellsprout, Ekans/Sandshrew, Mankey/Meowth, Growlithe/Vulpix, Nidoran♂/♀, Scyther/Pinsir, etc.) have been flattened into a single unconditional list per map, so species from both original versions are catchable in this one ROM. Since each map's wild list is a fixed-size table (`NUM_WILDMONS = 10` slots, see `constants/pokemon_data_constants.asm`), duplicate filler slots were traded away rather than the table being lengthened — most exclusive species show up at reduced frequency compared to their native version, not 1:1 rate parity. The Game Corner prize lineup (`data/events/prizes.asm`, `prize_mon_levels.asm`) was intentionally left on its Red-version selection (Nidorina, Scyther/Dratini/Porygon) since the Blue-side equivalents (Nidorino, Pinsir) remain obtainable via wild-caught evolution/Safari Zone. Cosmetic-only `_RED`/`_BLUE` branches that don't gate catchable content (Game Corner slot-reel graphics, SGB border palette, the title-screen's randomly-chosen Pokémon list, default player/rival name suggestions) were left alone and simply resolve to their Red-flavored asset now that only `_RED` is ever defined.
4. **"Pokémon Purple" rebrand, with a gothic pre-title intro**: the cartridge still identifies as `POKEMON RED` at the hardware level (untouched — changing that has wider ripple effects than the branding warrants), but the presentation layer is re-themed throughout. `gfx/version.asm`'s `Version_GFX` points at `gfx/title/purple_version.png` (a small hand-generated "PURPLE VERSION" logo bitmap, 11 tiles wide, replacing the old `red_version.png`/`blue_version.png`), and `engine/movie/title.asm`'s `VersionOnTitleScreenText` is a single unconditional sequential tile-code run matching that width (the old code had a red/blue-specific quirk of skipping some tiles and splicing in the normal font's space glyph — not preserved, not needed now that there's only one version string). Before the title screen, `home/init.asm` now calls `farcall PlayGothicIntro` (`engine/movie/gothic_intro.asm`) instead of jumping straight there — this plays a brief full-screen scene: a Victorian-gothic castle/graveyard silhouette (`gfx/title/gothic_intro_bg.png`, converted to a 144-unique-tile, 4-shade DMG image via `rgbgfx -u -T`) fades in, "PURPLE" stamps across it letter-by-letter with a thud sound (`gfx/title/gothic_intro_stamp.png`, an Impact-font wordmark), then it all fades back out into the normal `DisplayTitleScreen` sequence. (`title.asm` itself no longer touches the castle art at all — an earlier attempt tried to show it as a title-screen backdrop peeking through the gaps around the logo/character, but that VRAM region turned out to double as where the cycling Pokémon's front sprite loads, corrupting both; a dedicated pre-title scene sidesteps the conflict entirely and shows far more of the image besides.)

   Several non-obvious pitfalls got hit building this, worth remembering for any future title/intro graphics work:
   - **Regenerate `-u`/`-T` graphics as a pair, and don't let them drift**: `rgbgfx -u -T` produces a deduplicated tile sheet *and* a tilemap whose indices only make sense together. The `.2bpp` is gitignored and rebuilt by `make` (`*.2bpp` in `.gitignore`), but the `.tilemap` is a checked-in source file `make clean` does *not* delete (matching this repo's existing convention for e.g. `gfx/sgb/red_border.tilemap`) — if you regenerate one without the other (or forget the `RGBGFXFLAGS += -u -T` Makefile line for a new image entirely, so the generic `%.2bpp: %.png` rule quietly rebuilds it *without* dedup), the tile sheet and tilemap silently stop matching and you get a corrupted-looking image with no build error. Always regenerate both from the same `rgbgfx` invocation and check they're both freshly written.
   - **1bpp vs 2bpp loading**: a graphic converted with `rgbgfx --depth 1` (used for simple black/white logos and text, e.g. the version-text and intro-stamp wordmarks) must be loaded with `FarCopyDataDouble` (which expands each 1bpp byte into a 2bpp pair), not `FarCopyData`/`FarCopyData2` (which do a straight byte copy and assume the source is already 2bpp). Using the wrong one compiles fine and produces visually scrambled tiles at runtime.
   - **hWY vs rWY**: `hWY` (HRAM) is a shadow copy that the VBlank handler (`home/vblank.asm`) copies into the real `rWY` register every frame (unless `wDisableVBlankWYUpdate` is set) — writing `rWY` directly without also updating `hWY` gets silently overwritten back on the next frame. If the window layer ends up covering the whole screen with a blank tile (this happened during `gothic_intro.asm` development — the entire scene looked pure white despite correct tile/tilemap data), check `hWY`/`rWY` before anything else.
   - **wTileMap vs VRAM**: the *title screen's own* tile placement (logo, mon, copyright) is written via `hlcoord`-style addressing into `wTileMap` (a WRAM staging buffer, `ram/wram.asm`), not directly into `vBGMap0`/`vBGMap1` — an automatic transfer/`TitleScreenCopyTileMapToVRAM` mechanism syncs it at specific points in the bounce/scroll choreography, and direct VRAM writes get silently clobbered on the next sync. (`gothic_intro.asm` avoids this entirely: it's a static scene with the LCD off during setup, so it writes `vBGMap0` directly for the initial reveal, and uses the auto BG transfer — `hAutoBGTransferEnabled`/`hAutoBGTransferDest` — only for the letter-by-letter stamp updates once the LCD is on.)
   - **ROMX bank switching for `FarCopyData`-family calls**: any data pulled in via `INCBIN` that doesn't live in the *same bank* as the code reading it must be copied with a bank-aware routine (`FarCopyData`/`FarCopyData2`/`FarCopyDataDouble`, which take the source bank in `a`) — a plain `CopyData` silently reads whatever bank happens to be paged in at the time, not the bank the label's `BANK()` value implies.
   - Also: this ROM's `layout.link` hand-assigns **every** section to a specific fixed bank with no slack; growing an existing section (even by a few bytes, e.g. widening the version-text graphic) can overflow a completely unrelated section sharing that bank. New/grown data is safest given its own floating `SECTION "...", ROMX` (no explicit bank) so the linker can bin-pack it anywhere with room, rather than bloating a section that's already tightly pinned — this is how `gothic_intro.asm` and the widened version-text graphic are both declared.

5. **Hidden per-Pokémon power tier**: every individual Pokémon secretly carries a tier from 1-10 (5 = neutral), stored in the otherwise-vestigial `MON_CATCH_RATE` byte of the party/box struct (aliased `MON_TIER` in `constants/pokemon_data_constants.asm` — copied in when a mon is created but never read again for its original purpose, since the real catch-odds math uses a separate battle-only copy, `wMonHCatchRate`/`wEnemyMonActualCatchRate`). The tier applies a flat ±5%-per-step modifier to all 5 base stats (tier 1 = -20%, tier 10 = +25%; `ApplyTierModifier` in `engine/pokemon/tier_modifier.asm`, hooked into `CalcStat`'s base-stat read in `home/move_mon.asm`). Wild Pokémon roll their tier at battle-init time (`RollWildTier`, weighted toward low tiers, `data/pokemon/tier_chances.asm`); gym leaders (Brock–Sabrina, Giovanni) roll tier 6-8 for their mons live in `LoadEnemyMonData` (`engine/battle/core.asm`); every other trainer/rival/Elite Four mon and every gift Pokémon (starter, fossils, Eevee gift, Lapras, Hitmon*, Magikarp, Game Corner prizes, trades) stays neutral (tier 5). A custom 1-tile pixel-art badge (`gfx/status/tier_numerals.png`, 10 hand-drawn glyphs — thin tally bars for 1-4, a V for 5, V+bars for 6-9, an X for 10) shows next to the level on the party status screen's first page.

   **The wild-tier roll lives in `InitWildBattle` (`engine/battle/core.asm`), not in `TryDoWildEncounter` (`engine/battle/wild_encounters.asm`) where it originally was** — this was a real bug, caught after a caught Kakuna showed no tier badge at all. `TryDoWildEncounter` only runs for ordinary grass/water encounters; fishing rods (`engine/items/item_effects.asm`) and scripted single-mon encounters (Snorlax on Route 12/16, the legendary birds, etc.) set `wCurOpponent`/`wCurEnemyLevel` directly and skip `TryDoWildEncounter` entirely, jumping straight into `engine/battle/core.asm`'s shared `InitBattle`→`InitBattleCommon`→`InitWildBattle` chain — so a tier roll placed only in `TryDoWildEncounter` silently left every one of those mons with a stale/zero tier byte. `InitWildBattle` is the one point *every* wild battle passes through regardless of trigger, so that's where the roll belongs; rolling it any earlier, in a specific trigger path, will always miss some other trigger path.

   Since `CalcStat`'s `hl` argument doesn't reliably point at a struct with a `MON_TIER` byte at a fixed offset across all its call sites (two of them — `GetEnemyMonStat`'s scratch buffer and `LoadEnemyMonData`'s `battle_struct`-shaped `wEnemyMon` — use different layouts entirely from the party/box struct), the tier value is threaded through a dedicated HRAM byte (`hStatCalcTier`) that each caller sets immediately before calling `CalcStat`/`CalcStats`, rather than being derived structurally from `hl`. A second HRAM byte (`hStatCalcBase`) round-trips the base-stat value itself, because `ApplyTierModifier` is invoked via the `homecall` macro and `homecall`'s bank-restore `pop af` clobbers whatever `CalcStat` left in `a` — a register-based return value would just get silently discarded.

   `ApplyTierModifier` lives in its own floating `SECTION "Tier Modifier", ROMX` (`engine/pokemon/tier_modifier.asm`, included from `main.asm`) rather than inline in `home/move_mon.asm` — the fixed `Home` bank (shares ROM0 with the `NULL`/`rst`/interrupt vectors and the header, see `layout.link`) had zero slack and overflowed by 9 bytes the first time this was added directly.

6. **Eevee-only starter**: Professor Oak has one Pokémon to give, not three — `scripts/OaksLab.asm`'s 3-ball choice always yields `EEVEE` no matter which ball is examined (the 3 map objects/balls are still cosmetically on the table; picking any of them is identical). The rival receives Eevee too, narrated in the same "claimed a ___!" text; separately, `wRivalStarter` is rolled once per save among `EEVEE`/`JOLTEON`/`FLAREON`/`VAPOREON` (`RivalStarterOptions` table) to decide what his Eevee will have evolved into **starting from his 2nd wave of battles** (SS Anne, Pokémon Tower, Silph Co., Route 22's 2nd battle, and the Champion fight) — his first 3 encounters (Lab, Route 22's 1st battle, Cerulean City) are always plain Eevee, since he hasn't had story-time to evolve it yet. `data/trainers/parties.asm`'s `Rival1Data`/`Rival2Data`/`Rival3Data` and every trainer-number lookup that branches on `wRivalStarter` (`scripts/SSAnne2F.asm`, `PokemonTower2F.asm`, `SilphCo7F.asm`, `Route22.asm`'s 2nd table, `ChampionsRoom.asm`) were resized from 3-way to 4-way accordingly; the Champion's signature-move grant (`engine/battle/read_trainer_party.asm`) picks Thunder/Fire Blast/Blizzard/Double-Edge to match. The player no longer starts with any evolution stones outright — see item 8's cultist dream sequence, which is what actually grants the one stone they'll have access to. Title-screen mon cycling still shows the vanilla Bulbasaur/Charmander/Squirtle (cosmetic, untouched, doesn't reference "your starter").

   Eevee's innate level-1 moveset is `TACKLE, SAND_ATTACK` (`data/pokemon/base_stats/eevee.asm`) — both trainers' Eevee have it from the very start, since there's no level threshold to dodge (next learnset move, Quick Attack, isn't until level 27). At level 5 in the lab, both sides landing/missing on a coin-flip Tackle while Sand Attack stacks accuracy drops reads as unfairly swingy for a tutorial-tier fight, so Gary's Sand Attack is specifically stripped in `ReadTrainer`'s shared `.FinishUp` step (`engine/battle/read_trainer_party.asm`), gated on `wCurOpponent == RIVAL1 && wTrainerNo == 1` — i.e. only the lab battle, not his Route 22/Cerulean City encounters and not the player's own Eevee.

7. **Industrial-goth score**: the soundtrack is being redone track by track into original, dark, minor-key compositions with a driving industrial pulse — mood-inspired (the brief was "something like Marilyn Manson's *Sweet Dreams (Are Made of This)* cover"), never a transcription of any real copyrighted song; only the mood/genre hallmarks (relentless minor-key ostinato bass, sparse haunting lead, heavier duty-cycle tone) get borrowed, not actual melodies. Converted so far, each demonstrating a different flavor of the treatment (still more tracks to go — anything not listed here is still the bright vanilla original):
   - `Music_TitleScreen` (`audio/music/titlescreen.asm`) — the first one done, and the one that established the technique below. First pass just recolored the existing melody into minor and read as "the original, but lower"; the version that stuck was a full from-scratch recompose (new melody/harmony/bass) keeping only the original's proven note-length/rest skeleton for cross-channel sync.
   - `Music_Routes2` (`audio/music/routes2.asm`, plays during Oak's intro/naming sequence) — parallel-minor conversion of the existing melody (the lighter-touch version of the technique, no full recompose needed).
   - `Music_WildBattle` / `Music_TrainerBattle` (`audio/music/wildbattle.asm`, `trainerbattle.asm`) — **exception to the key-conversion approach**: these were already tense/chromatic in the original (Gen 1's battle themes lean dissonant by design), so there's no bright major scale to flatten. Only tempo/duty-cycle/vibrato got touched; pitch content is untouched (`Music_TrainerBattle` alone is ~1850 lines — not a safe hand-edit target with no audio preview regardless).
   - `Music_PalletTown` (`audio/music/pallettown.asm`) — the most aggressive rework yet, because the brief was specifically "much much slower... less skipping and bumping": parallel-minor conversion + a full octave dropped throughout + a drastic tempo cut, *plus* rhythm thinning (adjacent short repeated notes pairwise-merged into single longer notes, exactly halving the attack rate on the busiest arpeggio channel while preserving each pair's total duration exactly, so it stays in sync). Tempo/register/key alone reads as "slower," not "less bouncy" — the rhythm itself has to change for that.
   - `Music_MeetProfOak` (`audio/music/meetprofoak.asm`, plays when Oak stops you from walking into the grass) — full from-scratch rewrite for genuine horror rather than "sad": gutted down to a handful of isolated low notes separated by long silence per loop, built around a deliberate tritone (B against F natural) instead of a consonant interval, master volume and per-note envelope volumes both pulled down. The 3 channels are **deliberately not length-matched** here, unlike every other track — letting them drift out of phase reads as unpredictable/wrong, which suits a horror stinger; it would sound broken on a driving battle theme.
   - `Music_OaksLab` (`audio/music/oakslab.asm`, plays through Oak's "choose your Pokémon" table speech) — same sustained-brooding treatment as Pallet Town (parallel minor + octave drop + tempo cut), *not* the horror treatment, because it has to carry a long dialogue scene — that much silence would feel like the music cut out.

8. **Cultist dream sequence, replacing the free starting stones**: before the player ever takes a real step on day one, they dream of a cultist figure who asks 3 short branching questions; the answers determine which single evolution stone (Fire/Water/Thunder) they wake up having committed to — which is, in effect, their Eevee's evolution for that save. This replaced an earlier, simpler version of the same idea (item 6's "starting stones") that just handed over all 3 stones for free with no choice involved.
   - **Trigger point**: `scripts/RedsHouse2F.asm`'s `RedsHouse2FDefaultScript` — the very first script that runs the first time the player has a real overworld position on a fresh save (traced end-to-end: `MainMenu`→`StartNewGame`→`OakSpeech`→naming→`PrepareForSpecialWarp` to `REDS_HOUSE_2F`→`EnterMap`→`OverworldLoop`). This script's own `wRedsHouse2FCurScript` state **resets every time the map is re-entered** (it's not persistent), so the one-time gate is a real event flag, `EVENT_HAD_CULTIST_DREAM` (`constants/event_constants.asm`, tucked into the padding before `NUM_EVENTS` so it doesn't need any resizing) — checked and set exactly like `OaksLabDefaultScript`'s own guard.
   - **The cultist is a normal, tiny overworld sprite standing in the room, not a full-screen portrait**: the first version of this used `OakSpeech`'s "cutscene" toolkit (`GBFadeOutToBlack`/`ClearScreen`/`predef DisplayPicCenteredOrUpperRight` to show a full-screen `ChannelerPic`) — it built and ran, but froze with a corrupted screen the moment it played, because that whole pattern has **no precedent anywhere in this codebase for being invoked from a normal map script** — it's exclusively used from special pre-title/intro contexts (`PlayGothicIntro`, `OakSpeech` itself) that aren't reached via the standard per-frame overworld script dispatch. A regular room script keeps the map on screen the whole time and overlays sprites/dialogue on top of it (exactly `BillsHouse.asm`'s own NPC-walks-in-and-talks model), so the working version reuses that instead: the cultist is a real `object_event` (`data/maps/objects/RedsHouse2F.asm`, `SPRITE_CHANNELER` — the overworld version, not the trainer-pic one) sitting in the room from the start, hidden by default (`toggleable_objects_for REDS_HOUSE_2F` in `data/maps/toggleable_objects.asm`, `TOGGLE_REDSHOUSE2F_CULTIST` in `constants/toggle_constants.asm`) and simply revealed with `predef ShowObject`/hidden again with `predef HideObject` around the scene, exactly like every other scripted NPC reveal in this disassembly. **Lesson: a clean build is not evidence a cutscene-style scene will actually run correctly from a normal script context** — the freeze here had zero compiler/linker errors; only cross-referencing against what similar existing code actually does (and doesn't do) surfaced the problem.
   - **Second freeze, same lesson applied one level too shallow**: even after switching to the NPC-sprite model above, the sprite would appear but the scene still hung completely (no textbox, no input) — the fix that time was still calling `PrintText` directly from `PlayCultistDream` itself (a plain default-script function, called via `farcall`), instead of `DisplayTextID`. `PrintText` (`home/window.asm`) only draws a box and hands off to `TextCommandProcessor`; `DisplayTextID` (`home/text_script.asm`) additionally runs `farcall DisplayTextIDInit` first and, after the text finishes, `WaitForTextScrollButtonPress`/`HoldTextDisplayOpen`/`CloseTextDisplay` — without that init step nothing ever got drawn and input stayed locked. Every other auto-triggered narration script in this codebase (e.g. `OaksLab.asm`'s `OaksLabOakChooseMonSpeechScript`, `PalletTown.asm`'s `PalletTownOakHeyWaitScript`) calls `DisplayTextID` for this reason; `PrintText` only ever appears *inside* a `text_asm` block that `DisplayTextID` has already dispatched into (see `BillsHouse.asm`). Fixed by giving the cultist's intro/3 questions/outro their own `TEXT_REDSHOUSE2F_CULTIST_*` IDs and `text_asm` wrapper blocks in `scripts/RedsHouse2F.asm` (dialogue content itself lives in `text/RedsHouse2F.asm`, per the usual scripts/text split), with `PlayCultistDream` now just sequencing `ldh [hTextID], a` / `call DisplayTextID` for each one — it no longer calls `PrintText` at all. Since these `TEXT_` constants are needed from `engine/movie/cultist_dream.asm`, a different bank/object file than `scripts/RedsHouse2F.asm`, they need an explicit `EXPORT` (unlike a normal map's `TEXT_` constants, which only ever get referenced from within their own same-object-file script) — `dw_const`'s underlying `const` macro doesn't export by default, only `const_export` does. **Second lesson stacked on the first: matching one proven precedent (NPC sprite over full-screen portrait) isn't enough if a different piece of the same scene (raw `PrintText` over `DisplayTextID`) still deviates from what every other working example in the codebase actually does.**
   - **The answer menus** (`AskCultistQuestion` in `cultist_dream.asm`) are a hand-rolled variant of `DoBuySellQuitMenu`'s pattern (`engine/menus/text_box.asm`) rather than the item-list-driven `SPECIALLISTMENU` used for elevators — right tool, since the 3 answers per question are plain text, not items. Each question got its own new menu template constant (`CULTIST_Q1/Q2/Q3_MENU_TEMPLATE` in `constants/menu_constants.asm`, slotted into 3 previously-`const_skip`ped/genuinely-unused IDs) plus a `text_box_text` row in `data/text_boxes.asm`, all reusing the exact same box geometry as `BUY_SELL_QUIT_MENU_TEMPLATE`. Only `PAD_A` is watched (no B-button cancel) — the dream doesn't let you walk away without answering. `AskCultistQuestion`/`TallyCultistAnswer`/`DetermineCultistStone` are called via `farcall` from the `text_asm` wrapper blocks (a different bank than `cultist_dream.asm`), so they're exported (`::`); the 3rd question's own answer (needed as the tie-break) is threaded through a WRAM byte (`wCultistLastAnswer`) rather than a register, since each question is now a separate `DisplayTextID` round-trip rather than one continuous call chain. `AskCultistQuestion` also wraps its `DisplayTextBoxID` call in `SaveScreenTilesToBuffer1`/`LoadScreenTilesFromBuffer1`, matching `YesNoChoice` (the proven pattern for a menu popping up mid-scene over an already-drawn dialogue box) rather than `DoBuySellQuitMenu` (which never restores the screen itself, since it's only ever reached via a mart's own full-screen redraw afterward) — without this, 3 popups drawn back-to-back over one otherwise-static room scene had nothing erasing the previous question's box before the next one's prompt printed elsewhere on screen.
   - **Third freeze, a plain register-clobber bug introduced by the popup-cleanup fix above**: `AskCultistQuestion`'s first draft called `SaveScreenTilesToBuffer1` *before* `ld [wTextBoxID], a` — but `SaveScreenTilesToBuffer1` (`home/tilemap.asm`) clobbers `a` internally (it's a plain `hlcoord`/`CopyData` copy, not written to preserve a caller's register), so by the time execution reached `ld [wTextBoxID], a`, the incoming menu-template-ID argument was long gone, replaced with whatever `CopyData` happened to leave behind. `DisplayTextBoxID` then looked up that garbage ID in `TextBoxFunctionTable`/`TextBoxCoordTable`/`TextBoxTextAndCoordTable` and could land almost anywhere depending on what the leftover value happened to be — consistent with the bug manifesting differently across attempts (garbled-but-selectable one time, a hard freeze the next), since it's undefined behavior rather than one fixed failure mode. Fixed by storing `a` into `wTextBoxID` *first*, then calling `SaveScreenTilesToBuffer1` — `DisplayTextBoxID` itself reads the ID back out of `wTextBoxID`, not out of a live register, so this is the only ordering that's actually safe. General lesson: any time a fix introduces a *new* call before an existing `ld [wSomething], a`, check whether that new call clobbers `a` before the store happens — this is an easy mistake to reintroduce even after already having learned it once elsewhere in this codebase (see `hStatCalcBase`/`homecall` above, a different instance of the same underlying class of bug).
   - **Fourth bug, the real one behind "menu shows at the top-left with no visible text" — `farcall` clobbers `a` on *both* sides of the call, not just on return**: `scripts/RedsHouse2F.asm`'s question wrapper blocks did `ld a, CULTIST_Q1_MENU_TEMPLATE` / `farcall AskCultistQuestion`, and `AskCultistQuestion` returned its answer the same way (`ld a, [wCurrentMenuItem]` / `ret`, with the caller doing `ld [wCultistLastAnswer], a` right after the farcall). Both directions are unsafe: `Bankswitch` (`home/bankswitch.asm`) does `ld a, b` to load the *destination* bank right before `jp hl` into the callee, and does `ld a, b` again to reload the *source* bank right after the callee's `ret`, before its own final `ret` back to the call site. A value placed in `a` on either side of a `farcall` is gone by the time it matters. This was actually diagnosed by emulating the built ROM (see "Testing with PyBoy" below) and reading CPU registers directly at a hook placed on `AskCultistQuestion`'s entry point: `a` held `$01` (bank 1, `AskCultistQuestion`'s own `BANK()`) instead of the intended `$16` (`CULTIST_Q1_MENU_TEMPLATE`). Downstream, `DisplayTextBoxID` matched that stale `$01` against `MESSAGE_BOX` in `TextBoxCoordTable` instead of the real template in `TextBoxTextAndCoordTable` — drawing a blank bottom message box with no text (that table's match path never calls `PlaceString`) while `AskCultistQuestion`'s own cursor-placement code still ran and drew a bare `▶` at the literal top-left of the screen, exactly matching what was reported. Fixed by routing the value both ways through WRAM instead of registers: the caller now does `ld [wTextBoxID], a` itself before the `farcall` (so `AskCultistQuestion` just reads the already-set `wTextBoxID`, never receiving anything through `a` at all), and `AskCultistQuestion` writes its chosen answer to a new `wCultistAnswer` byte (`ram/wram.asm`) as its last action instead of returning it in `a`; `TallyCultistAnswer` and `DetermineCultistStone`'s tie-break both read `wCultistAnswer` directly. **Standing lesson for this codebase, corrected from an earlier note**: it is not just `homecall`'s bank-restore `pop af` that destroys a return value in `a` — plain `farcall`/`Bankswitch` does the same thing on *both* the call-in and return-out edge. Never pass or return a value through `a` across any `farcall`; always use a WRAM/HRAM byte instead, checked in both directions.
   - **Testing with PyBoy**: this environment has no interactive emulator, but a headless one can be scripted. `python3 -m venv /root/pyboy-env && /root/pyboy-env/bin/pip install pyboy Pillow` (needs `python3-pip`/`python3-venv` via `apt-get install`, and this WSL install ended up on Ubuntu 26.04 with Python 3.14). `pyboy.hook_register(bank, addr, callback, context)` places a breakpoint-like hook at a ROM address (get bank:addr pairs from `pokered.sym`, generated by every `make`) and fires `callback` every time the CPU executes it — from inside the callback, `pyboy.register_file.A/B/C/.../HL/PC` reads live CPU registers, which is what actually caught the `farcall` bug above (no amount of re-reading the source found it; direct register inspection did, on the first attempt). `pyboy.memory[addr]` reads/writes WRAM/HRAM directly (addresses also from the `.sym`). `pyboy.button("a", hold_frames)` queues a press auto-released after that many `pyboy.tick()` calls; `pyboy.screen.image.save(path)` dumps the current frame as a PNG. Caution: a map's WRAM state (e.g. `wCurMap`) can read as a plausible-looking value *before* the real game state is actually live (caught a false-positive "arrived in the target room" read this way, well before the intro/naming screens had actually finished) — a hook firing on a specific script/function's own entry point is a far more reliable "have we actually gotten here" signal than polling a WRAM value. The naming screen can be skipped instantly by pressing `start` (`.pressedStart` in `engine/menus/naming_screen.asm` submits immediately, even with an empty name) rather than navigating the letter grid. For tile-content questions (is tile X actually blank at runtime?), don't reason about VRAM layout/unions from source alone — read `rLCDC` (`pyboy.memory[0xff40]`) to get the real tile-addressing mode (`bit 4` clear = signed "$8800 method", base `$9000`, tile ID used as a signed byte; set = unsigned "$8000 method", base `$8000`), compute the real address for the tile ID in question, and read those 16 bytes directly out of `pyboy.memory[]` — this caught a bug (`ClearScreen`'s fill tile) that static analysis of the union/VRAM layout got wrong on the first pass.
   - **Directly unit-testing a single function via forced `PC`/`SP` (not just observing via hooks)**: push a "trampoline" return address (an infinite `jr -2` written into a scratch WRAM byte, e.g. `wCultistVotes`) onto the stack by hand (`sp = (pyboy.register_file.SP - 2) & 0xFFFF`, write the trampoline address there, then set `register_file.SP = sp`), set input registers, set `register_file.PC` to the target function's address, then `tick()` in a loop checking `register_file.PC == trampoline` to know it returned. Two non-obvious things have to be true first or this either hangs or silently executes the wrong code, both discovered the hard way debugging item 10's AI work:
     - **The Nintendo boot ROM overlay is still mapped over `0x0000-0x00FF` immediately after constructing `PyBoy(...)`**, since nothing has run the real boot sequence far enough to disable it. Any function living in that address range (e.g. `CopyData` at `0x00b5` in this build) will silently execute stale boot ROM bytes instead of the real cartridge code — not a crash, just wrong instructions, which then behaves like a hang or a jump into garbage. Fix: `pyboy.memory[0xFF50] = 1` once, right after construction, before any other setup. Confirmed by reading the raw bytes at the target address before/after this write and comparing against the actual `.gbc` file's bytes at the equivalent file offset (`bank*0x4000 + (addr - 0x4000)` for a switchable-bank address) — a real, provable diagnostic, not a guess.
     - **Calling a function in a non-zero bank needs *both* `pyboy.memory[0x2000] = bank` (the real MBC bank-select register write, confirmed to actually re-page the bank by comparing read-back bytes against the ROM file) *and* `pyboy.memory[hLoadedROMBank] = bank`** (the game's own HRAM shadow of "what bank is currently loaded," read by `homecall`/`Bankswitch` to know what to restore afterward) if the function you're calling (or anything it calls) uses `homecall`/`farcall`/`callfar` internally — e.g. `Divide` (`home/math.asm`) `homecall`s into a separate bank for the actual division. Skip the `hLoadedROMBank` write and the bank gets restored to something wrong partway through, and execution wanders off into unrelated code — which looks exactly like "the function has a bug" from the outside, and is a large part of why this specific investigation took as long as it did.
   - **Move ID and effect ID constants (`constants/move_constants.asm`, `constants/move_effect_constants.asm`) are commented with their value in hex, without a `$` prefix** (e.g. `const MEDITATE ; 60` means hex `$60` = decimal 96) — misreading one of these as decimal silently builds a test (or any other code) around the wrong move/effect entirely. Verify by counting: `grep -n "const [A-Z]" file.asm | awk -F: '{print NR-1, $0}'` gives the real positional (decimal) value independent of the comment, or cross-check the move's actual compiled bytes in `data/moves/moves.asm` against the ROM file at the right offset.
   - **Dialogue length budget applies here too, and got missed on the first pass**: several of this scene's `text`/`line`/`cont` segments ran well past the ~18-visible-character-per-line budget documented above (e.g. "and I shall whisper" at 20 chars, "back what you are to" at 21) — the box doesn't reject overlong lines, it just wraps mid-word at the character boundary and cuts the rest, which is what actually shipped and was caught from a screenshot showing "whisp" split from a wrapped "r". All of this scene's dialogue was rewritten and re-counted line-by-line (including the `<PLAYER>` token's worst-case ~7-character width) to fit.
   - **Scoring**: answer index 0/1/2 always means Fire/Water/Thunder regardless of each question's wording, tallied into 3 WRAM counters (`wCultistVotes`, `ram/wram.asm`). With exactly 3 votes cast, either one answer has an outright majority (2 or 3 — the other two mathematically can't also reach 2), or it's a 1-1-1 three-way split, in which case the third question's own answer is the tie-break ("your final answer seals it").
   - **Closing the loophole**: per explicit design intent, this is meant to be a real permanent commitment, not a flavor-only choice — `data/items/marts.asm`'s `CeladonMart4FClerkText` (Celadon Department Store 4F) was the *only* other legitimate source of any of the 3 stones anywhere in this ROM (no hidden items, no NPC gifts, no Game Corner/Safari Zone source), and had all 3 removed from its `script_mart` list (Leaf Stone/Poké Doll unaffected — Leaf Stone is unrelated to Eevee and still needed for other evolution lines).

   The reusable approach:
   - **Key**: parallel-minor conversion is the default move when adapting an existing bright melody — flatten the major 3rd/6th/7th relative to the original's major key (e.g. G major→G minor is B→A#, E→D#, F#→F; A major→A minor is C#→C, F#→F, G#→G) and leave the rest. This preserves a melody's contour/rhythm while genuinely darkening its color. A chromatic secondary-dominant leading tone (e.g. C#→D in G) is usually still valid tension in the parallel minor (same dominant) and is worth keeping wherever the original used that kind of pull. **Skip this step** if the source is already tense/chromatic rather than bright/major (see `Music_WildBattle` above) — there's nothing to flatten, and production/timbre changes carry the whole effect instead.
   - **Shifting a whole track's octave down by a fixed amount via find-replace is order-dependent and will silently corrupt notes if done carelessly**: naively replacing `octave 4`→`octave 3` and then `octave 3`→`octave 2` in two passes also re-shifts the notes the first pass just created, collapsing two different octaves into one. Either use a placeholder string for each source octave before writing any final values (`octave 4`→`OCTAVEPLACEHOLDER3` for every source value, only then resolve every placeholder to its real target in a final pass), or just rewrite the file from an already-read copy of the original in one pass. This bit `Music_OaksLab` mid-edit; caught before building, but only because the build was checked, not because anything would have flagged it otherwise — a wrong octave compiles fine.
   - **Channel roles** (for a fresh recompose): channel 3 (wave) carries the driving root-fifth ostinato pulse (mostly repeated/alternating notes — this is the single biggest lever for the "industrial" feel); channel 1 (pulse, `duty_cycle 1` for a buzzier/more aggressive tone) carries a sparser, more haunting lead than a typical bright fanfare; channel 2 (pulse, `duty_cycle 2` for more body) fills harmony, favoring safe tonic/dominant/minor-third chord tones so it stays consonant without needing to be individually verified against channel 1; channel 4 (noise/drums) usually doesn't need to change.
   - **Timbre**: slower tempo than the original bright version (larger `tempo` value = slower), deeper `vibrato`, and `note_type` envelopes tuned for a more sustained/droning character over a quick bright decay. For genuine horror rather than "sad," also pull the master `volume` and per-note envelope volumes down, and consider leaning on rests/silence over notes.
   - **"Less skipping/bumping" means the rhythm has to change, not just the tempo**: slowing a busy, evenly-subdivided rhythm down doesn't remove its bounciness, it just bounces slower. To actually smooth it out, pairwise-merge adjacent short notes into fewer longer ones — merging two adjacent notes of length N each into one note of length 2N preserves the exact total duration (so sync with other channels is untouched) while genuinely halving the attack rate.
   - **When adapting an existing track** (as opposed to composing fresh), keep every channel's exact note-length/rest/`sound_call`/`sound_loop` skeleton identical to the source and only change pitch/duty/envelope/tempo values — this guarantees the 4 channels stay in sync without needing to verify by ear. When composing fresh, still keep each channel's own internal note-length arithmetic consistent so loops don't drift — except when the goal is specifically an unsettling/horror feel, where deliberately letting channels drift out of phase (see `Music_MeetProfOak` above) is a feature, not a bug.
   - **Constraint to remember**: there is no audio playback in this working environment, so every change here is composed by reading/writing note data blind, never verified by ear before being handed off. Treat first attempts as a draft and expect an iteration round based on what it actually sounds like.

9. **SGB screen-colorization cleanup**: this game's presentation is meant to read as clean black/white/gray on real hardware and SGB alike, not tinted — several stray SGB palette definitions (all leftover vanilla decoration, none of them gating real artwork) were flattened to plain white (`RGB 31,31,31` ×4) rather than recolored: `PAL_SGB1`/`PAL_SGB2`/`PAL_SGB3` (`data/sgb/sgb_border.asm`, under `IF DEF(_RED)`) each colorize a different region of the SGB *border* graphic (the decorative frame surrounding the 160×144 game screen, distinct from anything in-game) — they originally rendered as a pink/salmon, green, and blue-purple dotted pattern respectively (the border art itself uses a checkerboard dither of 2 DMG shades to fake a mid-tone gray on real hardware; SGB colorizing those two dither shades as *different hues* turns the smooth gray into visible two-color dots).
   - **A second, unrelated dot pattern was inside the game screen itself, not the border**: the title screen's own background (behind the logo/version text/character, colorized via `PAL_LOGO2`/`PAL_LOGO1`/`PAL_MEWMON` in `data/sgb/sgb_palettes.asm`, per `BlkPacket_Titlescreen` in `data/sgb/sgb_packets.asm`) kept showing a tinted dot texture even after the border fix above, because it's a completely different bug: `engine/movie/title.asm`'s `ClearBothBGMaps` fills the whole background with the char literal `' '`, which the project-wide charmap (`constants/charmap.asm`) resolves to tile `$7F` — not actually blank in `gfx/font/font.png` (confirmed by decoding the raw 1bpp tile data), but the small raised "." glyph the copyright string itself uses as a date separator (`.tileScreenCopyrightTiles`). On plain DMG grayscale this is nearly invisible (the glyph is a single dark pixel-cluster on an otherwise-identical-toned background), but SGB colorizing shade 0 and shade 3 as genuinely different hues per region turns it into a visible tiled dot pattern across the whole "blank" background — a real, provable, 100%-unmodified-vanilla quirk (confirmed via `git log` showing neither `font.png` nor this fill line have ever been touched in this fork's history), just never visible/noticed on plain DMG or with the original muted palette choices. Fixed by having `ClearBothBGMaps` fill with `$40` instead — a genuinely all-zero tile in the font sheet, used as a raw numeric tile index (bypassing the charmap entirely) rather than a char literal. Also flattened `PAL_LOGO2`/`PAL_LOGO1`(`_RED`)'s shared background color (`31,29,31`, a hair off pure white) to `31,31,31` — safe since color 0 is exclusively the background/blank shade in every one of these palettes, never used for the logo or version text (confirmed by decoding `pokemon_logo.2bpp`'s actual shade usage before touching anything).
   - **`PAL_MEWMON` is shared across screens that shouldn't all change together — don't whiten it directly**: an earlier pass also flattened `PAL_MEWMON`'s background color the same way, on the reasoning that it's the palette `PalPacket_Titlescreen` (`data/sgb/sgb_packets.asm`) uses for the title screen's Pokémon-cycling backdrop. True, but `PAL_MEWMON` is *also* `PalPacket_PartyMenu`'s, `PalPacket_TrainerCard`'s, and `PalPacket_Generic`'s first palette slot (the naming screen included) — so that one change silently re-tinted the naming screen, party menu, and trainer card too, which surfaced as an unrelated-looking "why is the naming screen whiter now" report. Reverted `PAL_MEWMON` back to its original value and added a new, title-screen-only palette instead — `PAL_TITLEMON` (`constants/palette_constants.asm`, appended after the existing `PAL_GAMEFREAK` entry so no other palette's index shifts; matching new row appended to `SuperPalettes` in `data/sgb/sgb_palettes.asm`, same colors as `PAL_MEWMON` but with a pure-white background) — and pointed `PalPacket_Titlescreen`'s 3rd `PAL_SET` argument at it instead of `PAL_MEWMON`. General lesson: before whitening (or otherwise editing) any named palette in this file, grep `data/sgb/sgb_packets.asm` for every `PAL_SET`/`ATTR_BLK` that references it — a palette shared by multiple unrelated screens needs its own dedicated copy for a screen-specific tweak, not a direct edit.
   - **This environment's emulator can't actually show SGB colors, so verify these changes by re-deriving them from the packet/palette data, not by screenshot**: PyBoy (see the testing note below) renders Game Boy output in plain DMG grayscale — it has no SGB colorization support at all — so a screenshot from it will never show whether an SGB palette edit did what was intended, only whether the ROM still boots and runs. `assert_table_length NUM_SGB_PALS` passing at build time (i.e. the `SuperPalettes` row count still matches the enum count after appending a new entry) is the correctness check available here for this specific class of change. It's still possible to catch a *tile-content* bug this way even without color, though — see the next entry.
   - **The dot/stripe texture was still there after all of the above, because the earlier fix patched the wrong buffer**: `ClearBothBGMaps` clears `vBGMap0`/`vBGMap1` directly in VRAM, but the title screen's own tile placement (logo, mon-cycling area, copyright — see the pitfall list under item 4) is written into `wTileMap`, a WRAM staging buffer, via `hlcoord`; an automatic transfer syncs `wTileMap` to real VRAM afterward, which is what's actually shown on screen. `ClearScreen` (`home/copy2.asm`) — a much more widely-used function, not title-screen-specific — is what clears `wTileMap`, and it had the exact same char-literal-resolves-to-a-non-blank-glyph bug `ClearBothBGMaps` did, completely independently: `ld a, ' '` (→ tile `$7F` via the charmap). Caught by loading the built ROM into PyBoy (see below) and reading `wTileMap`'s WRAM bytes directly — every "blank" cell in the mon-cycling area really did hold `$7F`. Given this game runs with `LCDC` bit 4 clear (the "$8800 signed" tile addressing mode, confirmed by reading `rLCDC` live rather than assuming), tile `$7F` (a small positive value) resolves to VRAM address `$9000 + $7F*16 = $97F0` — landing inside the title screen's own loaded logo/copyright graphics, not inside the normal font at all; read directly, those 16 bytes are a real, non-blank alternating-row pattern, which is what tiled into the visible stripe/dot texture. Fixed the same way: `ld a, $40` (a numeric tile index, not a char literal, so it bypasses the charmap) — confirmed via the *same* live-VRAM-read technique that `$40` resolves to `$9000 + $40*16 = $9400`, which really is all-zero bytes at runtime, not just in the source PNG. **This was the second time a plausible-looking fix turned out to be treating the wrong memory region for this exact class of bug (`ClearBothBGMaps` vs `wTileMap`/`ClearScreen`) — when a fix to one "clear the screen" function doesn't fully resolve a reported visual bug, check whether a *different*, more central clearing function shares the same root cause before concluding the bug has a new, unrelated source.**
   - **The same `ld a, ' '` bug exists in roughly 30 more places across this codebase** (`grep -rn "ld a, ' '"` from the repo root turns up hits in `home/window.asm`, `home/vcopy.asm`, `home/text.asm`, `engine/battle/core.asm`, `engine/battle/animations.asm`, `engine/gfx/hp_bar.asm`, `engine/battle/print_type.asm`, `engine/pokemon/status_screen.asm`, `engine/link/cable_club.asm`, `engine/items/town_map.asm`, `engine/menus/pokedex.asm`, `engine/menus/start_sub_menus.asm`, `engine/overworld/player_state.asm`, `engine/movie/hall_of_fame.asm`, `engine/movie/credits.asm`, `engine/movie/trade.asm`) — **only the two feeding the title screen (`ClearScreen`, `ClearBothBGMaps`) have been fixed so far**; the rest are an open, documented latent-bug class (same invisible-on-DMG, SGB-colorization-dependent visibility) rather than something confirmed to visibly affect gameplay yet. Worth a systematic pass if this class of artifact turns up reported on any other screen — don't assume it's already covered by the title-screen fixes above, since those only touched two specific call sites, not the pattern everywhere it occurs.
   - **Lesson**: two visually similar "dotted background" complaints in the same session had two unrelated root causes (a border palette left over from an earlier fix, and a mismatched charmap/tile-index assumption in unrelated title-screen code) — worth re-deriving from raw tile/graphic bytes each time rather than assuming a second report of "still dotted" means the first fix was incomplete in the same file. Decoding the actual `.1bpp`/`.2bpp` tile bytes directly (which DMG shade index is genuinely all-zero, which shades a given graphic actually uses) turned "probably the background tile is blank" into a provable yes/no, and is much more reliable than reasoning about SGB `ATTR_BLK` inside/border/outside semantics from memory.

10. **Smarter trainer battle AI, staying within pure Gen 1 mechanics**: permadeath (item 1) raises the real stakes of every trainer battle, but vanilla Gen 1's AI barely reacts to the battle state at all. This is a scoped set of fixes and additions to the two existing AI subsystems in `engine/battle/trainer_ai.asm`/`engine/battle/core.asm` — no held items, no new stats, nothing structurally "Gen 2." Regular trainer classes (Youngster, Bug Catcher, etc.) deliberately get **no** new move-choice logic here — only the universal switch-in fix below, which applies to every trainer regardless of class. Sharper move-choice logic is reserved for the roster that already gets hand-written item-use AI (gym leaders, Elite Four, Cooltrainers, Giovanni, Blackbelt, Agatha, Lance, and the rival's 2nd/3rd battles specifically — **not** his 1st, tutorial-adjacent lab battle).
    - **`AIGetTypeEffectiveness` (`core.asm`) used to stop at the first matching `TypeEffects` row instead of considering both of the defender's types** — pret's own comment already flagged this ("doesn't take into account the effects that dual types can have"). Replaced with a new `GetTypeMatchupMultiplier` (input: attacking type in `d`, defender's type1/type2 in `b`/`c`; output: a 16-bit multiplier in `hl`, `EFFECTIVE`(10)=neutral, up to 40 for a real 4x weakness like Onix vs. Water) that mirrors the real damage calc's own type-matchup walk (`core.asm`, just below) — which already correctly stacks both defender types — but accumulates a multiplier instead of scaling actual damage, staying read-only (never touches `wDamage`/`wMoveMissed`) so it's safe to call from AI scoring. A mono-type defender is handled correctly (one matching row applied once, not squared) since each `TypeEffects` row can only match type1 *or* type2 per row, never both. This also incidentally fixed a second, self-canceling bug: the old function initialized its result to hex `$10` (decimal 16) with a comment saying it should've been the named `EFFECTIVE` (decimal 10) — and `AIMoveChoiceModification3`'s own `cp $10` check was written to match that *same* wrong value, so the two bugs canceled out for the "no matching row" case by pure coincidence of hex/decimal notation. Fixed by starting the new accumulator at the real `EFFECTIVE` and updating Modification 3's check to compare against the named constant instead of the magic number.
    - **The single highest-leverage fix: `EnemySendOut`'s switch-in mon selection (`core.asm`) was pure "first unfainted mon in party order," for every trainer in the game, no matchup awareness at all** — not just an AI-opt-in issue like the move-choice modifications, since this is the *one* function both a deliberate mid-battle switch (`SwitchEnemyMon`) and automatic replacement of a fainted mon (`ReplaceFaintedEnemyMon`) funnel through. Replaced with `AIChooseBestSwitchIn`, which scores every eligible candidate (not fainted, not the currently-active slot) by (offensive potential against the player's current mon) minus (defensive risk from it), each computed via `GetTypeMatchupMultiplier`, biased by a constant `+400` so the unsigned 16-bit subtraction never needs separate sign handling (both terms are always 0–40 in practice, so the true result is always representable). Deliberately routes every intermediate value through new WRAM scratch bytes (`ram/wram.asm`) rather than juggling registers across several `GetTypeMatchupMultiplier` calls — this function only ever runs on an actual switch decision, never once per frame, so the extra loads/stores cost nothing that matters, and it made the logic far easier to get right and review than nested push/pop bookkeeping would have. Ties are broken by earliest party order (deliberately not also by HP, to keep the first version simple to verify). The very first send-out of a fresh battle is unaffected, since exactly one candidate exists at that point regardless of scoring — confirmed directly (see testing notes below), not just assumed.
    - **Two new move-choice "modifications," extending the existing `AIMoveChoiceModificationFunctionPointers` system** (`trainer_ai.asm`) rather than writing a parallel one: Modification 4 (previously dead code, just `ret`) discourages re-using a stat-boosting move whose relevant stat is already maxed at +6 stages — a direct complement to Modification 2 just above it, which encourages stat-boosting moves unconditionally, blind to whether the stat is already capped. Modification 5 (new) is a kill-shot heuristic: if the player's mon is at or below 1/4 HP and a strong/super-effective damaging move is available, heavily favor it — deliberately a cheap heuristic (HP fraction + type effectiveness), not a real damage-formula estimate, to avoid new Z80 damage-math arithmetic that would've been much harder to get right and to verify. Wired into `data/trainers/move_choices.asm` per the scoping above.
    - **A real, would-have-shipped bug: Modification 5 called `GetTypeMatchupMultiplier` with a plain `call` across a bank boundary.** `GetTypeMatchupMultiplier` lives in `engine/battle/core.asm` (bank `0x0f`); `AIMoveChoiceModification5` lives in `engine/battle/trainer_ai.asm` (bank `0x0e`). A `call` is just a 3-byte instruction with a raw 16-bit address — RGBASM/RGBLINK don't track which bank the caller happens to be executing from, so this assembled and linked cleanly, and would have silently executed whatever ROM data happened to be paged in at that address at runtime instead of the real function, for every Modification-5-enabled trainer whenever their mon dropped below 1/4 HP with a damaging move in its kit — i.e., precisely the tense, low-HP moments in exactly the boss fights this change was meant to sharpen. The existing, already-correct `AIMoveChoiceModification3` had the answer sitting right above it the whole time: it calls `AIGetTypeEffectiveness` (the *wrapper*, not `GetTypeMatchupMultiplier` directly) via `callfar`. That distinction matters and is the actual lesson: `farcall`/`callfar`'s `Bankswitch` protocol clobbers `b` (loaded with the destination bank right before the jump) and `hl` (loaded with the target address) — so it's only safe to `farcall`/`callfar` a function whose calling convention doesn't depend on live input registers surviving the jump. `AIGetTypeEffectiveness` reads `wEnemyMoveType`/`wBattleMonType1`/`wBattleMonType2` straight from WRAM and writes its result to `wTypeEffectiveness`, also WRAM — no register inputs to lose — so calling *that* across the bank boundary is safe, while calling `GetTypeMatchupMultiplier` (whose whole calling convention is `b`/`c`/`d` register inputs) the same way is not. This is the same underlying class of bug as the cultist dream sequence's `farcall` register-clobber (item 8) — caught here for the *third* time this project, which says the lesson is worth restating plainly: **before adding a `farcall`/`callfar` to any function, check what that function's calling convention actually is — if it takes register inputs or returns a register output, farcall is unsafe for it regardless of which specific registers happen to be involved this time.**
    - **How this was actually verified**: a clean `make` under `-Weverything` caught none of the above — not the cross-bank bug, not the type-effectiveness fix's correctness, nothing behavioral. Verified instead by directly unit-testing the built ROM in PyBoy: a small reusable harness pushes a "trampoline" return address (an infinite `jr -2` written into unused WRAM) onto the stack, sets input registers, jumps the CPU's `PC` straight to a target function's address (from `pokered.sym`), and ticks until execution lands back in the trampoline, at which point the output registers/WRAM are read directly — effectively a unit test for a single Z80 function with no need to play through to a real battle. This caught the cross-bank bug directly: the call would time out or land at a nonsensical `PC` instead of returning. Two non-obvious environment quirks had to be worked out before this technique was reliable, both now folded into the testing note below (Nintendo boot ROM overlay on `0x0000-0x00FF`; `homecall`/`Bankswitch`'s bank-restore bookkeeping needing `hLoadedROMBank` kept in sync with the real MBC bank-select poke). Every claimed fix above (`GetTypeMatchupMultiplier`'s dual-type math including the mono-type non-double-counting case, `AIChooseBestSwitchIn`'s matchup-based pick *and* its deterministic tie-break *and* its fainted-mon skip, Modification 4's maxed/not-maxed threshold, Modification 5's HP-gate and effectiveness-gate, each independently) was confirmed this way with a specific expected value, not inferred from the code reading correctly.
    - **Two of the "failures" hit along the way were bugs in the *test*, not the game** — worth remembering next time a test disagrees with the code: (1) move ID constants in `constants/move_constants.asm` are commented with their value in **hex without a `$` prefix** (e.g. `const MEDITATE ; 60` means hex `$60` = decimal 96, not decimal 60 — decimal 60 is actually `PSYBEAM`); reading one of these comments as decimal silently tests the wrong move entirely. (2) Water is *not* super-effective against Grass — Grass resists Water in every generation — so a test asserting "Water Gun should be encouraged against a Grass-type target" was asserting the wrong expected outcome, not catching a real bug in the effectiveness check. Both were only caught by cross-checking against the actual compiled ROM bytes / real Gen 1 type chart rather than trusting a remembered assumption.

When touching dialogue in `text/*.asm`, keep to this Victorian-gothic despair tone, respect the ~18-visible-character-per-line budget for `text`/`line`/`cont`/`para` segments (the display box is 20 tiles wide; this matches the longest lines found in the original shipped/checksum-verified game), and preserve the existing macro skeleton (same count of `line`/`cont`/`para`/`done`/`prompt`) so box paging doesn't change.

When touching `data/wild/maps/*.asm`, remember there's no more `_RED`/`_BLUE` split to preserve — any new encounter added there just needs to keep the flat list at exactly `NUM_WILDMONS` (10) `db LEVEL, SPECIES` lines (`def_grass_wildmons`/`def_water_wildmons` assert this at build time).

## Build commands

Requires **rgbds 1.0.2** (`brew install rgbds` on macOS; see `INSTALL.md` for other platforms).

```sh
make              # builds pokered.gbc (the only ROM this fork produces)
make red          # same as above, explicit target name
make clean        # remove build artifacts (objects, compiled gfx, roms)
make RGBDS=path/to/rgbds/  # use a local rgbds install instead of the global one
```

There used to be a `pokeblue.gbc`/`pokeblue_debug.gbc` build path; it's been removed from the Makefile (see "Single merged ROM" above), so `make blue`/`make blue_debug` no longer exist.

`make compare` runs `sha1sum -c roms.sha1` to verify a byte-perfect rebuild — this is the project's only "test," and it references upstream pokered/pokeblue checksums that no longer apply here at all. **Don't rely on it on this fork.** A successful `make` (no assembler/linker errors under `-Weverything`) is the correctness bar for changes.

There's no separate lint step — `rgbasm`/`rgblink` are invoked with `-Weverything -Wtruncation=1`, so build warnings are the linting.

### Versioned ROM builds

Recompiled ROMs worth keeping go in `Roms/vX.Y/` (e.g. `Roms/v0.1/pokered.gbc`). This folder is gitignored (`/Roms/` in `.gitignore`) — bump the version folder each time you want to snapshot a build, don't commit the `.gbc` files themselves. ## Architecture

The disassembly mirrors the original ROM's bank layout; `main.asm` and `includes.asm` are the entry points that stitch everything together (`includes.asm` pulls in every file under `constants/` and `macros/` globally — they don't need per-file includes).

- **`constants/`** — global constant definitions (`rsreset`/`rsset` struct layouts, enums). `constants/pokemon_data_constants.asm` defines the party/box Pokémon struct (`MON_HP`, `MON_STATUS`, `PARTYMON_STRUCT_LENGTH`, etc.) referenced throughout `engine/` and `data/`.
- **`macros/`** — assembly macros, notably `macros/scripts/text.asm` (the `text`/`line`/`cont`/`para`/`done`/`prompt` text-printing DSL used by everything in `text/`).
- **`home/`** — "home bank" routines callable from anywhere via `rst`/`call` without a bank switch (party menu drawing, text printing, core utility functions).
- **`engine/`** — the actual game logic (battle engine in `engine/battle/`, menus in `engine/menus/`, overworld events in `engine/events/`, item effects in `engine/items/`), organized by subsystem.
- **`data/`** — static game data: trainer parties (`data/trainers/parties.asm`), Pokémon base stats, move data, etc.
- **`scripts/`** — one file per map, containing the event/warp/NPC-trigger logic for that location. Scripts reference dialogue via `text_far` pointers into `text/`.
- **`text/`** — one file per map (matching `scripts/`), containing the actual dialogue/sign/menu text for that location, using the macros from `macros/scripts/text.asm`.
- **`maps/`** — map blockset/tileset binary data and map header definitions (`maps.asm`).
- **`ram/`** — WRAM layout definitions (`ram/wram.asm`); this is where per-map state like `wPartyMon1HP` etc. lives.
- **`gfx/`, `audio/`** — graphics and music/sound source data.
- **`tools/`** — small C helper programs used by the build (graphics conversion, patch generation, include scanning) — see `tools/Makefile`.
- **`vc/`** — Virtual Console-specific constants/patches (the `red_vc` build target, not part of normal builds).

A useful mental model for dialogue work: `scripts/<Map>.asm` decides *when* text prints (`text_far _SomeLabelText`), and `text/<Map>.asm` defines *what* that label actually says. The label name is shared between the two, so grep for the label to jump between trigger logic and prose.
